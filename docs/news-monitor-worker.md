# Cloudflare publication monitor

This monitor checks served AI-trends pages only. It does not generate articles, change the site, deploy the site, inspect Actions status or dispatch recovery. Its deployment is independent of GitHub Actions, using an existing Cloudflare account, Workers Cron and **SQLite-backed** Durable Objects. The public-page/date/body contract is shared with the Node CLI in `scripts/ai-publication-core.mjs`.

## Schedule, state and resource bounds

The scheduler invokes every minute. It calls the single DO every minute on Tue/Thu/Sat 07:00–10:30 JST inclusive, and every fifth minute otherwise. One tick observes at most **one issue**. The current due issue takes priority in the minute window; retained failures are round-robin outside it. With N active failed issues, each can take roughly 5N minutes to be revisited, and old issues wait during a new due issue's morning window. Old state is never silently relabeled to the new issue.

A successfully observed on-time issue is silent and stops being fetched. A negative completed observation at/after 10:30 records one failure; later verified public content records recovery without clearing the deadline miss. An initial positive only after the deadline emits a monitoring-uncertainty alert, never fabricated failure/recovery. Cron does not guarantee execution at exactly 10:30:00; use completed check time and preserve uncertainty if observation was lost. HTTP 200, JSON timestamps and Actions success do not prove publication.

The single SQLite DO retains per-issue state, stable delivery IDs and metadata. It uses the SQLite-backed KV API (not a legacy paid-only KV namespace), no WebSockets, no keep-alive loop and no alarms. `blockConcurrencyWhile` serializes full ticks; duplicate/older scheduled timestamps are ignored. The platform's 30-second block limit fails a stuck tick; public fetches are individually limited to 10 seconds/2 MiB, Slack requests to 2 seconds/16 KiB. Each lookup follows at most three same-origin redirects; no public source links are fetched. Credentials and response bodies are not logged.

Self-imposed caps are UTC-day tick 1,800, publication observations 600 and Slack post attempts 16 (the final slot is reserved for a quota alert), total issues 1,000, active issues 16 and state per issue 8 KiB. Quota failure stops further publication I/O and never purchases capacity, resets issue state or drops pending events. Daily counters can reset the following UTC day; retention overflow halts permanently for operator inspection. These caps bound **this monitor**, not account-wide usage; free capacity remains a shared-account preflight gate. Max retained issue payload is roughly 8 MiB plus metadata, keys, delivery records and SQLite overhead; typical state is much smaller.

Per observation: two public resources (usually four HTTP requests with canonical redirects; upper limit eight), one DO invocation per tick, metadata and one issue read/write. A send adds a delivery read, a durable pre-send attempt write, a post-result write, quota writes and issue acknowledgement. Slack identity checks add one read-only `auth.test` HTTP request before every new send. Do not count network waiting as CPU; DO wall duration includes it. CPU/free limit and real usage must be verified on the deployed runtime, not inferred from local timing alone.

## Limited Slack delivery and uncertain acknowledgement

Allowed alerts are publication deadline failure, delayed recovery, and monitor anomalies (late/gapped tick, deadline observation unknown, quota/retention limit, adapter/delivery error). Ordinary publication success is never posted. Unresolved health codes retain their first/last observation across UTC day changes; each is notified at most once per UTC day. Clock/state corruption fails closed with a sanitized log when safe deduplication cannot be established.

Before a post, persist `delivery:EVENT_ID = attempting`. Only HTTP 200 with Slack `ok: true`, the exact channel and a message timestamp marks `sent` and acknowledges the issue event. Missing/invalid/oversized responses, HTTP errors/timeouts or wrong-channel replies become `unknown` (explicit `ok: false` is `rejected`). **All existing attempts, including rejected/unknown/attempting, suppress automatic resend.** This prioritizes avoiding duplicates over guaranteed delivery; it is not exactly-once delivery. A crash after accepted Slack delivery but before local acknowledgement retains the attempt, so restart does not resend.

An unacknowledged failure blocks recovery posting. Inspect Slack and the durable attempt before an explicitly authorized manual reconciliation; never delete the attempt to force a retry. Preserve unknown pending issue state and IDs even if this consumes active retention. No automatic reconciliation/resend endpoint is exposed. Remote KV-state inspection/reconciliation requires a separately approved maintenance revision using the DO storage API; this change exposes no public admin route. A confirmed sent record can be acknowledged on the next tick after a local persistence interruption.

## Monitoring limitations and rollback

A later surviving Cron can detect a >6-minute tick gap or >90-second scheduling lag. **The same Cron cannot detect its complete shutdown**, nor can Slack report a failure when credentials, storage, Slack or Cloudflare are unavailable. A separately hosted heartbeat watcher is not installed here. Site and monitor share Cloudflare, so provider-wide outages are a common failure domain even though GitHub runner/Actions failures are independent.

Stopping Cron is the reversible operational rollback; retain the DO namespace and state. Do not delete migrations, namespace, storage or notification attempts. No production Cron/namespace exists from this change yet. Real plan/usage, authorized credentials and deployment confirmation remain the outstanding activation conditions.
