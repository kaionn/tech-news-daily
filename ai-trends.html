今号のテーマ DECISION-MODELS

「選ぶだけ」の判断は生成モデルから外れ始めた — 選択肢を一度に採点する専用モデル、確率で決める閾値、ルーティングと検査への配置

エージェントの中には、文章を書かずに「選ぶだけ」の判断が多い。このクエリで Web 検索を走らせるか、どのモデルに回すか、ツールの出力にプロンプトインジェクションが紛れていないか。これまではこうした判断も生成型 LLM に JSON で答えさせるのが普通で、出力トークンの課金、数百ミリ秒から数秒の待ち時間、表記揺れのパースを毎回払っていた。11 月 11 日に Google が Gemini Decisions API を、12 日に Perplexity が Decider v1.3 を公開し、9 月に Jev を出した TypeSafe AI を含め、3 社が「閉じた選択肢を採点して確率を返す」専用モデルを揃えた。今号は、判定を生成から切り離す設計がどの層で実装され、返ってきた確率をどう使い、パイプラインのどこに置かれているかを並べる。

TL;DR — 3 行で
  • 判定専用モデルは文章を生成せず、事前に与えた選択肢を採点して確率を返す。Gemini Decisions API は 1 リクエストで最大 1,000 問を共有入力に対して評価し、出力トークンは常に 0。Perplexity Decider は複数の質問を 1 回の forward pass で答える
  • 確率が返る以上、どこで切るかはアプリ側の設計になる。Google のドキュメントは confidence が 0.7 未満なら人のレビューに回す例を示し、閾値は自分のトラフィックのラベル付きデータで決めるよう求めている。数値の多くはベンダー自身の評価で、自社データでの検証が前提
  • 置き場所はモデルルーティング、ツール出力の安全検査、エージェントログの見直しに集まっている。Perplexity は 7,000 セッション分のログを 1 日で読ませてセキュリティルールの見落としを洗い出したが、ルール修正の承認は人が行う
📐 パターン 1: 判定を生成から切り離す — 選択肢を一度に採点する

判定専用モデルの入出力は、生成型 LLM の構造化出力とは形が違う。Gemini Decisions API（モデル gemini-decision-1）は、共有の input と、キーごとの questions を受け取る。質問の型は yes/no の noul、選択肢から選ぶ choice（2〜255 択）、順序付きルーブリックで採点する score の 3 つだ。応答は質問ごとに確率と confidence を返し、usage の total_output_tokens は常に 0 になる。モデルはトークンを 1 つずつデコードせず、選択肢をまとめて採点する。Perplexity の Decider v1.3 も同じ形をとる。各質問の末尾にマーカートークンを置き、そこから決定ヘッドが選択肢のスコアを読み出すので、同じ入力に対する複数の質問を 1 回の forward pass で答えられる。v1.3 では、共有された状態はすべての質問を参照し、各質問は状態と自分のトークンだけを参照する。質問どうしが直接影響し合わない構成にして、結果を安定させている。

この形に収束した理由は、判定の呼び出し回数が生成の呼び出し回数を大きく上回るからだ。1 つのユーザー入力に対して、検索の要否、モデルの選択、安全性、ツールの選択と、問いは複数並ぶ。生成型で答えれば、問いの数だけ出力を待ち、パースし、表記揺れを処理することになる。Google は共有入力を 1 リクエストにつき 1 回だけ課金し、質問 1〜100 問の範囲で遅延がほぼ一定（16K トークンまでの文脈で end-to-end 150〜250 ms）だとしている。出力の型が選択肢に閉じているので、パースの失敗もない。代わりに失うのは自由記述で、理由の説明や新しい選択肢の提案はできない。判定に理由が必要な場面では、生成モデルが引き続き担当する。

Google Gemini Decisions API（gemini-decision-1）
共有入力 1 つに最大 1,000 問を投げ、yes/no・多肢選択・ルーブリック採点を確率付きで返す。出力トークンは課金されない
公式ドキュメントによると、入力は最大 262,144 トークンをテキスト・画像・音声・動画・PDF で共有でき、質問はその文脈枠の範囲で 1〜1,000 問を指定できる。価格は入力 100 万トークンあたり $0.10、出力は $0。Google は Gemini 3.5 Flash-Lite を Interactions API で使う場合と比べて、同じベンチマーク群でほぼ 5 分の 1 のコストだとしている。遅延と較正誤差の数値は Google 自身の評価

Qwen3.8-27B ベースの判定モデルと、Qwen3.5-4B に蒸留した Flash 版を Apache ライセンスの重みで公開。複数の質問を 1 回の forward pass で答える

📐 パターン 2: 確率が返るなら、閾値と逃がし先は自分で決める

判定モデルの出力は「答え」ではなく「確率分布」なので、どこで切るかはアプリ側の仕事になる。Gemini Decisions API の confidence は「最上位の答えが正しい確率の推定値」で、yes/no では max(noul, 1 - noul) に等しい。ドキュメントの例では、confidence が 0.7 未満なら "human_review" に回す。閾値は自分のトラフィックからラベル付きの例を集め、偽陽性と偽陰性のコストを比べて決めるよう書かれている。選択肢の設計にも注意書きがある。choice は必ず選択肢のどれかに確率を配るので、範囲外の入力には "other" のような受け皿を用意するか、先に yes/no で対象かどうかを確かめる。選択肢はアルファベット順に並べ替えられるため、"none_of_the_above" のように位置に意味を持たせたキーは避ける。

ここに設計が集まるのは、判定モデルの価値が確率の信頼性にかかっているからだ。生成型 LLM に「自信度」を数字で書かせても、その数字が正答率と対応する保証はない。TypeSafe AI は Jev を Reinforcement Learning for Calibrated Decisions（RLCD）で訓練し、確信度が高いほど正答率も高くなるよう較正したと主張する。Perplexity は、選択肢の並べ替え・ラベルの付け替え・ラベル名の変更をしても意味上の答えが変わった割合を測り、Decider v1.3 が 0.27%、Jev 1.14 が 2.69〜4.84% だったと報告した。ただし、どの数値もベンダー自身の評価だ。Perplexity も閾値は固定値を仮定せず、小さく代表的なラベル付き開発セットで調整するよう勧めている。各社とも、確率をそのまま信じてよいとは書いていない。

TypeSafe AI Jev（System One Models）
自由記述を生成せず、事前に定義した型の値を較正済みの確率付きで返す判定モデル。出力は無料、入力は 100 万トークンあたり $0.042
公式ブログは end-to-end 70〜500 ms、System One 型の問いで最先端 LLM より 40〜200 倍速いと主張する。速度測定は創業者の西海岸のノート PC から行ったものだと明記し、評価の参照解答に他社の最先端モデル 2 つの平均を使ったため OpenAI と Anthropic のモデルに有利な偏りがありうると認めている。Perplexity は Decider をこの Jev に着想を得たと書いており、この設計パターンの起点にあたる
📄 一次ソース
示唆: 判定モデルを入れるときは、モデルより先に「本番トラフィックから抜いた数百件のラベル付きデータ」を用意する。閾値・範囲外入力の受け皿・低確信度のときの逃がし先（人のレビュー、上位モデル、既定値）の 3 点を決めずに導入すると、確率が返ってきても結局 argmax を使うだけになる。
📐 パターン 3: 判定モデルを置く場所 — ルーティング、ツール出力の検査、ログの見直し

公開された事例は、置き場所がおおむね 3 つに分かれる。1 つめはモデルルーティングで、Gemini Notebook は Decisions API でクエリを適切なモデル階層と思考レベルに振り分け、日常的なクエリの遅延を最大 40% 下げたと Google は発表している。Perplexity は埋め込みモデルの上に複数の分類ヘッドを載せ、そのうち 1 つでクエリが Web 検索を必要とするかを決める。2 つめはツール出力の検査で、Google 検索は MCP ツール向けの安全レイヤーにこの API を使い、Perplexity もツール出力に含まれるフィッシングやプロンプトインジェクションの検出を用途に挙げる。3 つめはオフラインの見直しだ。Perplexity はエージェントのログをルールベースのチェックで監視し、Decider に「フラグが立たなかった記録にルールの見落としはないか」「立ったアラームは誤検知ではないか」を判定させた。

3 つに共通するのは、エージェントの本体ではなく、本体の前後や外側に置かれていることだ。どれも 1 回あたりの判断は単純だが件数が多く、生成型 LLM で回すとコストと遅延が積み上がる。Perplexity の例では、Decider は 1 日で 7,000 セッション・10 億トークンのログを読み、14 件のルール修正につながる欠陥を見つけ、うち 6 件が 2 日以内に承認・反映された。1 週間分のログで再生すると、最も件数の多いルールの発報量は 52% 減った。ただし、修正案を作るのは別のエージェントで、反映にはセキュリティチームのメンバーの承認が要る。判定モデルは大量に読んで候補を絞る役で、ルールを書き換える権限は持っていない。

Perplexity（Decider によるセキュリティルールの見直し）
ルールベースの監視が出した結果と出さなかった結果の両方を Decider に読ませ、見落としと誤検知を洗い出す。修正の承認は人が行う
公式ブログによると、ルールが外れた記録はトリアージ用のエージェントに渡り、そこでルール修正案を作り、セキュリティチームのメンバーが承認する。社内では他に、クエリ分類（63 タスクで本番の分類器より平均 6.54 ポイント高い正解率）、検索結果の再ランキング、クロールしたページの品質フィルタ、強化学習のロールアウト監視にも使っている。精度の比較はいずれも自社のテストスイートによる

📄 一次ソース
示唆: 判定モデルは、件数が多く、1 回の誤りが致命的でない判断から入れる。ルーティングとツール出力の一次スクリーニングが最初の候補になる。権限の付与やルールの変更のように、誤りの影響が大きい判断では、判定モデルを候補を絞る役に限り、最終決定は人か別の検証段に残す。
✍️ 編集後記 判定専用モデルの登場で目立つのは、速さや安さより「LLM に何を書かせないか」が設計の対象になったことだ。選ぶだけの判断を生成から外すと、残った生成の呼び出しは理由の説明や文章の作成といった、本当に文章が要る仕事に絞られる。ただし、確率が返ってきても閾値を引くのはこちら側で、そのためのラベル付きデータを用意するのは、どのベンダーも代わりにやってくれない。
