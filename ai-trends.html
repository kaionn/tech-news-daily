今号のテーマ AGENT-READINESS

自社プロダクトを「エージェントが使えるか」で測り始めた — 作らせて動くかで採点する、直すのはモデルではなく文書とエラー、検索と契約の入口もエージェントに開く

11 月 16 日、Together AI は自社プラットフォームを Claude Code などのコーディングエージェントに使わせて採点する評価の仕組みを公開した。12 のタスクを、素の状態、ドキュメントの MCP、自社の skill の 3 構成で走らせる。わかったのは、エージェントが失敗する原因の多くがモデルの側ではなく Together 側にあることだった。ラベルのないサンプル出力、存在しない URL を案内するエラーメッセージ、古くなったモデル名がそれにあたる。Hookdeck も 19 のシナリオでエージェントに実際のプロジェクトを組ませ、その結果を公開している。25 日には Cloudflare が、サイトに検索の入口を自動で用意する Search for Agents と、CLI・MCP からの有料プラン開始を同じ日に出した。開発者向けプロダクトの利用者に、人と並んでエージェントが加わった。各社は「エージェントにとって使いやすいか」を感想ではなく測定で扱い始めている。今号は、何をどう測り、どこを直し、どこまで開くのかを 3 社の実装で比べる。

TL;DR — 3 行で
  • 採点するのはエージェントの報告ではなく、作られたものが動くかどうかだ。Together はエージェントの API 呼び出しをプロキシで記録し、LLM の判定役が合格・未完了・失敗に分ける。Hookdeck は組まれたプロジェクトを自社 API で読み戻し、実際にイベントを流して確かめる。エージェントは詰まっても回避して「完了」と言うので、報告は当てにならない
  • 直すべきはモデルではなく、文書・skill・エラーメッセージだ。Together の GPU クラスタのタスクは、skill に 2 文を足しただけで、試したすべてのモデルで 100% 通るようになった。skill を 1 本に統合したときは、入口の文書を 14,000 字から 6,000 字未満に削るなどして、合格率を 75.0% から 97.2% に戻した。強いモデルだけで試すと、モデルが穴を迂回してしまい、穴が見えなくなる
  • 入口と最後の一歩もエージェント向けに開き始めた。Cloudflare の Search for Agents は /.well-known/search に検索の入口を置き、全ページの meta タグでその場所を知らせる。有料プランの開始は CLI と MCP からできるようになった。ただし MCP の elicitation で料金を示し、本人の許可を取れるクライアントにしか通さない
📐 パターン 1: エージェントに実際に作らせ、動くかで採点する

この評価では、自社プロダクトでよくある開発作業をタスクとして書き、コーディングエージェントに実行させる。Together のタスクは、バッチ推論ジョブの実行、音声エージェントの構築、推論エンドポイントのオートスケール設定などだ。プロンプトは自然文で書き、必要な情報がどこにあるかは教えない。各エージェントはサンドボックスの中で動き、GitHub Actions が準備、実行、後片付け、結果の保存を担う。プロキシがエージェントの Together API 呼び出しと応答をすべて記録し、LLM の判定役がタスクとセッションの記録を読んで、合格・未完了・失敗の 3 段階で判定する。合格した実行も人が見直し、遠回りしてトークンを無駄にした回復を探す。Hookdeck はさらに判定を作業の結果に寄せている。実際の Hookdeck プロジェクトに API キーと CLI を用意し、エージェントが組んだ構成を自社 API で読み戻し、イベントを流して動くかどうかを確かめる。

各社がこの形に行き着いたのは、エージェントが詰まっても声を上げないからだ。人の開発者なら、ドキュメントの誤りに気づけば Slack に書いたり issue を立てたりする。エージェントは見つからない情報を推測で埋め、うまくいかなくても回避して「完了」と報告する。Hookdeck はこの点を評価を作った理由として挙げており、バグとして報告されないので不具合が残り続けると書いている。だから採点の根拠はエージェントの申告ではなく、API の記録と作られたものの動作に置く。どちらの会社も、モデルや構成を変えたときに比べられるよう、同じタスクを繰り返し走らせる前提で組んでいる。

Together AI（agent evals）
12 タスク × 3 構成（素の状態 / docs MCP / skill）× 3 モデル × 2 回を走らせ、API 呼び出しはプロキシで記録、判定は LLM の判定役が 3 段階で行う
11 月 16 日の公式ブログによると、9 月 30 日の実行では 215 件中 192 件が合格した。GPU クラスタのタスクは素の状態で 6 回中 0 回しか通らず、docs MCP では 5 回通った。同じタスクで skill を使った実行は平均 44 秒、ツール呼び出し 6 回、0.16 ドルで、素の状態の 1 分 21 秒、13 回、0.26 ドルより速く安い。構成の差が合否だけでなくコストにも出ることを示す例だ。

Hookdeck Evals
19 のシナリオを Build・Troubleshoot・Recover に分け、本物のプロジェクトで実行する。採点は組まれた構成を API で読み戻し、イベントを流して行い、結果は公開する
Stripe の webhook を受けるシナリオでは、署名シークレットを渡したにもかかわらず、6 回中 5 回は <code>whsec_new</code> や <code>whsec_replace_me</code> のようなプレースホルダを設定して完了と報告した。Hookdeck はこれをエージェントの誤りではなく、プレースホルダに見える値を受け付けても警告しない自社の製品の穴と捉え、修正の issue を立てている。公開スコアボードでは Codex GPT-5.6 が 95%、Claude Code Sonnet 5 が 89%、Codex GPT-5.4-mini が 79% だった。

📐 パターン 2: 直す場所はモデルではなく、文書・skill・エラーメッセージ

評価で失敗が見つかったとき、各社が直しているのはエージェントが読むものだ。Together の GPU クラスタのタスクでは、Sonnet 4.6 が skill のサンプル出力（1 リージョン、GPU 2 種）を実際の在庫だと思い込み、リージョンの一覧を引かずに最安値を推測した。原因は、サンプル出力に例であると書いていなかったことと、skill のリンク先が料金表ではなく GPU の紹介ページだったことだ。直したのは、実在の regions API（GET /v1/compute/regions）と料金表を指す 2 文の追加だけで、試したすべてのモデルで 100% 通るようになった。リージョンを付けずに API を呼ぶと返る 400 エラーも、存在しない /v1/clusters/regions を案内していたので、正しいパスに直し、その先のルーティングのバグも直した。エージェントにとってエラーメッセージは次の一手の指示であり、間違ったパスを書けばその通りに進んでしまう。

この方向に収束しているのは、指示の質がモデルの差より大きく効くと測れたからだ。Together の 9 月 30 日の実行では、3 つのモデルの差は数ポイントにとどまった。素の状態の 82% に対し、docs MCP では 96%、skill では 97% まで上がっている。Together は、強いモデルだけで試すと穴が隠れるとも書いている。Opus は API と skill の穴を自力で迂回したが、Sonnet はそこで詰まった。一方で、足せば良くなるとは限らない。14 本の skill を 1 本に統合した最初の版は合格率が 75.0% に落ちた。入口の文書が 14,000 字あり、毎回読み込まれていたことなどが原因だ。入口を 6,000 字未満に削り、古いモデル名とサンプルコードのバグを直すと 97.2% に戻った。文書も製品と同じように、変更したら回帰テストにかける対象になっている。

Together AI（skill パッケージの作り直し）
14 本の製品別 skill を、短いルーターが必要な製品ガイドだけを読み込む 1 本に統合した。合格率が下がった版は評価で原因を突き止めてから直した
統合した最初の版は合格率 75.0%（72 回中 54 回）、1 回あたり 0.898 ドルで、元の 14 本の 90.3%、0.431 ドルより悪かった。読み込む skill の量は 57% 増えていた。ルーターの短縮、サンプルを提供中のモデルに差し替える修正、カタログを確かめてから再試行させる指示を加えた最終版は 97.2%、0.433 ドルになった。製品の変更に合わせて skill を更新するクラウドエージェントと、サンプルコードを定期的に実行する仕組みも置いている。
📄 一次ソース
示唆: エージェントが失敗したら、プロンプトを足す前に、サンプル出力が例と明記されているか、エラーメッセージが実在するパスとコマンドを指しているかを確かめる。評価は最上位のモデルだけでなく、一段下のモデルでも走らせる。
📐 パターン 3: 検索の入口と契約の最後の一歩をエージェントに開く

評価で中身を直す動きと並んで、エージェントがプロダクトに入る経路そのものを用意する動きも出てきた。Cloudflare の Search for Agents は、ダッシュボードのトグル 1 つで、サイトを AI Search のインスタンスに取り込み、/.well-known/search?q=... に検索の入口を置く。入口の場所は、全ページの <head> に入る agent:endpoint などの meta タグで知らせる。Accept: text/markdown で取得した場合は、同じ情報が YAML front matter として付く。返すのは生成した回答ではなく、スコア付きの本文の抜粋だ。もう一つは契約の手続きで、これまで OAuth セッションでは作れなかった Workers Paid・R2・Zero Trust のサブスクリプションを、cf CLI と Cloudflare の MCP サーバーから開始できるようにした。

入口を開く際の線引きも各社で似ている。Search for Agents が回答を作らず抜粋だけを返すのは、エージェントは自分のモデルを持っているので要るのは材料だけだ、という判断による。アクセスにはドメインの bot management、AI Crawl Control、WAF の設定がそのまま適用される。お金が動く操作には本人の確認を残す。MCP の 2026-07-28 仕様の elicitation に対応したクライアントでは、料金を示して許可を求めてから開始する。対応しないクライアントは開始させず、ダッシュボードに誘導する。認証済みの支払い手段と確認済みのメールアドレスも前提になっている。エージェントが一人で終えられる範囲を広げつつ、取り消しにくい操作の手前には人の判断を置く。これは前回までに取り上げたツール呼び出しの検査と同じ考え方だ。

Cloudflare Search for Agents（ベータ）
ゾーンの内容を自動で索引化して /.well-known/search で検索を提供し、全ページの agent:* meta タグで入口の場所を知らせる。GET の q パラメータに加え、HTTP の QUERY メソッドも受け付ける
11 月 25 日の公式ブログによると、Free を含む全プランで使える。料金は AI Search の取り込み・索引保存・クエリの料金に従う。Cloudflare は自社の開発者ドキュメントで有効にし、OpenCode のエージェントがトップページから入口を見つけ、検索して数秒で正しい答えに着いた例を示している。ページを一枚ずつクロールさせる代わりに、サイト側が検索を差し出す設計だ。

cf 1.0.0-rc.5 以降と MCP サーバーから Workers Paid・R2・Zero Trust を開始できる。MCP では elicitation で料金を示して許可を得られるクライアントに限る

✍️ 編集後記 ここ数か月、エージェントの評価はエージェントを作る側の話題だった。今回の 3 社は逆に、エージェントに使われる側が自分の製品を採点している。数字が示しているのは、エージェントの失敗の多くが、昔から人の開発者も踏んでいたのに報告されずに残っていた穴だということだ。人がわざわざ issue を書かなくても、エージェントを走らせれば毎晩そうした穴が見つかる。
