今週のテーマ RAG

RAG 構成パターンの現在地 — naive RAG はもう使われていない

「文書をチャンクに割ってベクトル DB に入れ、質問に似たチャンクをプロンプトへ注入する」— 2023 年に量産されたこの構成（naive RAG)を、2026 年半ばの主要プロダクトはほぼ使っていない。理由は単純で、実運用に載せた途端「型名やエラーメッセージのような完全一致クエリを意味検索が拾えない」「上位チャンクがノイズだと回答ごと壊れる」という 2 つの穴を必ず踏むからだ。今週は主要プロダクトの公開情報を突き合わせ、現在の標準構成と、その先で設計が分かれるポイントを整理する。

TL;DR — 3 行で
  • hybrid search（キーワード + ベクトル）が事実上の既定。ベクトル単独の新規採用はもう少数派
  • re-ranking は「コーパスが大きく引用が製品価値」の場合に限って割に合う。全員に必要な段ではない
  • agentic RAG は常時ではなく「検索スコアが低いときだけ発動」の条件付きが現実解として定着しつつある
📐 パターン 1: Hybrid Search が既定になった理由

現在の標準は、BM25 などのキーワード検索とベクトル検索を並走させ、RRF（Reciprocal Rank Fusion）でスコアを統合する 2 系統構成だ。ベクトル検索は「言い換え」に強い代わりに「完全一致」に弱い。TypeError: cannot read properties のようなエラーメッセージ、関数名、社内プロダクトのコードネーム — 実ユーザーのクエリの相当数は意味ではなく文字列で引くべきもので、この取りこぼしはチャンク設計や埋め込みモデルの改善では直らない。構造的な欠陥は構造で埋めるしかない、というのが各社が同じ結論に至った理由よ。

注目すべきは、ハイブリッド化と同時に「検索段で権限・鮮度のフィルタを済ませる」設計が広がった点。生成段に渡してから捨てるのではなく、そもそも見せてはいけない文書を検索結果に出さない。RAG がセキュリティ境界を兼ねるようになった、と言い換えてもいい。

GitHub Copilot Chat（コードベース検索）
シンボル索引（完全一致)+ 埋め込み検索の並走。どの索引を引くかをルーターが先に判定する
コード検索は「関数名で引く」「やりたいことで引く」の 2 モードがはっきり分かれる領域で、ハイブリッドの効果が最も出やすい。クエリの種類に応じて索引を選ぶルーター層を挟むのが特徴。

📄 Notion 公式技術解説（一次ソース）
自分のプロダクトへの示唆: これから RAG を組むなら最初からハイブリッドで始めるのが順当。pgvector + PostgreSQL 全文検索、あるいは Elasticsearch 単体でも両系統を賄える。ベクトル DB を先に選定して後からキーワード検索を足すと二重管理になりやすい。
📐 パターン 2: Re-ranking を挟む境界線

検索上位 50〜100 件を cross-encoder（クエリと文書を同時に読む精密な関連度モデル）で並べ替え、上位 5〜10 件だけをコンテキストに入れる構成。初段の検索は「速いが粗い」、re-ranker は「遅いが正確」で、この 2 段構えは情報検索の古典的な設計がそのまま LLM 時代に持ち込まれた形だ。

ただし今年に入って「全員に必要な段ではない」という線引きがはっきりしてきた。追加レイテンシ 100〜300ms と推論コストを払う価値があるのは、コーパスが大きくノイズ候補が多い場合と、引用付き回答そのものが製品価値である場合。社内ナレッジ検索程度の規模なら、ハイブリッド検索の統合スコアだけで十分な精度が出る事例報告が増えている。

判断基準: コーパス 10 万チャンク未満・社内利用なら re-ranking なしで始めて、回答品質の実測で必要性を判断するのが順当。顧客向けで引用付き回答を出すなら初期から必須寄り。Cohere Rerank や BGE-reranker のようなマネージド / OSS の選択肢が揃い、導入自体の障壁は低くなった。
📐 パターン 3: Agentic RAG は「検索のやり直し」から始まった

クエリ書き換え・多段検索・検索結果の自己評価をエージェントループに任せる agentic RAG が今年の主戦場だ。ただ、バズワードの印象と違って実装の現場は保守的で、「1 回目の検索スコアが閾値未満のときだけクエリを書き換えて再検索する」という条件付き発動が現実解として広がっている。全クエリをエージェント化すると、レイテンシは数倍、コストは 5〜10 倍になり、単純な質問（大半を占める）では品質がほぼ改善しないからだ。

つまり分岐点は「検索失敗をどう検知するか」に移っている。検索スコアの分布、上位チャンク間の一致度、生成前の関連度自己評価 — 失敗検知の精度が agentic 段の費用対効果を決める。ここは各社の公開情報が最も薄い部分でもあり、来月以降の発信が待たれる領域よ。

Perplexity（検索パイプライン）
クエリ分解 → 並列検索 → 統合を常時実行する全面 agentic 型
検索が製品そのものなのでコストを全面的に許容する側の代表例。逆に言えば、検索が製品の一機能に過ぎないプロダクトが同じ構成を真似る理由はない。
📄 CTO インタビュー（一次ソース）
自分のプロダクトへの示唆: agentic 化は「常時 or なし」の二択ではない。まず検索スコアのロギングから始めて、失敗クエリの実態を掴んでから条件付き再検索を足すのが低リスクな導入順。
✍️ 編集後記 3 パターンを並べると「LLM を信じず、検索を工学する」方向に業界全体が回帰しているのが分かる。RAG の品質問題は生成側ではなくほぼ検索側で決まる — この認識が共有された 1 年だったと言えるわね。基礎から知りたい人向けの用語解説（BM25 / RRF / cross-encoder)は tech-learning-daily 側に置いてある。
