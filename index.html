DEEP DIVE: GitHub の新 Git ストレージ設計 — 5,000 エージェントが 1 リポジトリへ同時 push

GitHub が AI エージェントの大量並行 push に耐えるため、Git ストレージを作り直した。11/4 の Universe 関連報道では「従来比 180 倍のスループット」という目標値だけが伝えられたが、GitHub Engineering Blog が設計の中身を公開した。出発点は、AI エージェントの増加で 1 つの忙しいリポジトリのリクエスト数が 3 月から 5 月で約 4 倍になったことだ。従来のようにサーバのローカルディスクを正本とする構成では、書き込みの調整コストがボトルネックになる。新設計（Project Rubicon）は「調整を最小化する」と「ストレージとコンピュートの分離」を原則とする。Git オブジェクトは不変なので、書き手同士が合意しなくても保存できる。順序付けが必要なのは参照（ref）の更新だけである。リクエストは使い捨ての仮想レプリカ（Spokes 経由）に振り分けられ、ローカルディスクはキャッシュにすぎない。パックは Azure Blob Storage に置き、参照とパックのマニフェストは Ref-CAS という複製ログが持つ。書き込みは「パックを Blob にアップロードし、Ref-CAS で 1 トランザクションをコミット」の 2 手順で済む。Ref-CAS は quorum による compare-and-swap で、触る参照だけをロックし、オブジェクト本体は保持せず、毎秒数万オペレーションを処理する。社内テストでは 5,000 の並行エージェントが単一リポジトリへ毎秒 7,200 push を送り、読み取りレイテンシは低いままだった。単一 blob の write-ahead log は毎秒数百書き込み止まりで、シャード分割では読み取りが遅くなったため採用を見送った。バックグラウンドのノードがシャードごとのリースでセグメントを封じ、パックを階層的にマージして、push 増加時もパック数を一定に保つ。現状は限定プライベートプレビューで、全体展開は来年初頭の見込みである。
🧠 「オブジェクトは不変、順序が要るのは ref だけ」という整理は、Git の性質をそのままスケール設計に使っており筋が良い。ただし 7,200 push/s は社内ベンチマークの値で、実際のエージェントの push パターンや巨大モノレポで再現するかは未検証だ。ブランチ単位ロックで 3〜4 倍という別報道の数字と合わせても、利用者が体感する差は来年の展開後にしか分からない。
  • 5,000 並行エージェントから単一リポジトリへ毎秒 7,200 push、読み取りレイテンシは低位を維持
  • 単一 blob の WAL は毎秒数百書き込みで頭打ち。Ref-CAS は触る参照だけをロックして毎秒数万オペレーションを達成
  • Azure Blob Storage + 使い捨てレプリカ構成。限定プライベートプレビュー中で、広範な展開は来年初頭
💡 エージェントで同一リポジトリに大量 push する運用は今後ホスティング側が受け止める前提になるが、それまでは push 頻度とブランチ分割の設計を自前で考えておくこと。

  • 最大 294,839 回線（個人 204,157・法人 90,682）、本人確認書類番号や一部で銀行口座情報を含む
  • 個別システムの脆弱性ではなく、連携システムを連鎖的にたどる設計上の弱点が悪用された
  • 11/4 検知、11/5 確認、11/6 公表。同期間に別件で 5G SA 障害（最大約 159 万人、コアスイッチのメモリ障害）も発生
