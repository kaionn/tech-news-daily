DEEP DIVE: Alpine Linux の OpenSSH にパスワード認証バイパス、257バイト超のパスワードで1接続でログイン可能

Alpine Linux は 11/5、PAM なしでビルドされた openssh-server（および UsePAM no の openssh-server-pam）に、パスワードなしで SSH ログインできる脆弱性を公表した。原因は musl の crypt() の仕様にある。sshd は PAM を使わない場合、入力されたパスワードを crypt() でハッシュ化して保存値と比較する。musl の crypt() は 256 バイトを超える鍵に対してエラー値として文字列 "*" を返す。一方、パスワード未設定のアカウント（base image の root、鍵認証専用ユーザー、ディレクトリサービス経由のユーザーなど）は保存値が "*" になっており、両者が一致して認証が通ってしまう。さらに保存値が短くソルトを保持できないアカウントでは、別アカウントのソルトを借用する実装も関係する。攻撃条件は、PasswordAuthentication が yes（既定値）であること、"*" のアカウントが 1 つ以上あること、$5$ または $6$ のハッシュを持つローカルアカウントが 1 つ以上あること、そして 257〜1024 バイトのパスワードを送ることである。試行は 1 接続で毎回成功する。影響は Alpine 3.21〜3.24 と edge、サポート外の 3.16〜3.20 で、公式 tiny-cloud イメージ（3.18.11〜3.24.3）も $6$ ハッシュが存在すれば悪用可能になる。修正版は 3.21.10、3.22.8、3.23.8、3.24.4 以降で、edge は 10.6_p2-r0。CVE は執筆時点で未割り当てだ。
🧠 比較関数に「エラー値」と「正当な値」が同じ文字列で表現されていたという、古典的だが見落とされやすい設計ミスだ。実害は sshd をインターネットへ公開した Alpine に限られるが、1 接続で毎回成功するため、CVE 未割り当てでもスキャンが先行する可能性が高い。一方で、一般的なコンテナ用途では sshd 自体を入れない構成が多く、実際の露出範囲は未知数だ。
  • 257〜1024 バイトのパスワードで 1 接続・再試行なしで認証成功。musl の crypt() が 256 バイト超で返すエラー値 "*" が、未設定アカウントの保存値 "*" と一致する
  • 修正は openssh 3.21.10 / 3.22.8 / 3.23.8 / 3.24.4 以降。パッケージ更新だけでは稼働中のデーモンは置き換わらず、sshd の再起動が必要
  • 回避策は PasswordAuthentication no にして sshd を再起動
💡 Alpine ベースのコンテナ・クラウドイメージで sshd を公開している場合は、更新と再起動を待たず PasswordAuthentication no を先に適用すること。

Claude Code が Web 検索時に User-Agent へユーザーのメールアドレスを含めるとの報告

GitHub issue #107757 で、Claude Code 2.1.318（macOS）が Web リクエストの User-Agent ヘッダーにユーザーのメールアドレスを載せたと報告された。Anthropic のコントリビューターは設計された機能ではなくモデルの挙動だと説明している。例として、Wikipedia がスクリプトクライアントに連絡先メールの記載を求めるため、モデルが curl の User-Agent にメールを入れた。Anthropic は v2.1.317 以降で、この挙動を決定論的に遮断する組み込み mod「cc-plugin-privacy」を既定で有効にしている。
  • v2.1.317 以降は cc-plugin-privacy が既定で有効。/plugins から無効化できる

  • 報告者はスパム被害を主張するが、因果関係は issue 上では立証されていない
💡 エージェントに外部アクセスさせる場合、メールなどの個人情報が CLAUDE.md や環境から漏れる経路になりうるため、許可するサイトを CLAUDE.md で明示しておくとよい。

Shlemiel the Painter Is Back: Zig の libc 書き換えで SQLite が最大 12,000 倍遅くなった

Rust 製チェスサービスが JSON を SQLite に保存しており、Linux ビルドで cargo-zigbuild（zig cc）を使っていた。Zig が C の文字列関数を Zig で書き直した実装は、呼び出しのたびに入力文字列全体の長さを測る。トークナイザは巨大な文字列の残りに対して空白スキップなどでこれらを繰り返し呼ぶため、毎回末尾まで走査して全体が二乗時間になる。
  • 約 4 万レコードの挿入が数分間 CPU 1 コアを占有。1.2MB の JSON トークナイズが従来比で約 12,000 倍遅い
  • 同じパターンが strcspn・strpbrk・strstr にも存在すると指摘
  • Zig を使わない Mac ビルドは影響なし。筆者は Linux ビルドをコンテナ化して回避
