今号のテーマ IN-HOUSE-MODEL-TRAINING

エージェント製品は「API で借りるモデル」から「自社ハーネスで鍛えたモデル」へ — オープンウェイトの土台、コスト込みの報酬、検証できる部品から内製する順序

コーディングエージェントの各社が、フロンティアモデルを API で呼ぶだけでなく自社モデルを出すようになった。Cursor の Composer、Cognition の SWE シリーズ、そして 10 月 8 日に JetBrains が公開した Mellum2.1。どれもゼロからの事前学習ではなく、公開済みのオープンウェイトモデルを土台に、自社のツール・サンドボックス・評価環境の中で強化学習（RL）をかけている。共通点は、モデルの差よりも「どのハーネスで、何を報酬にして鍛えたか」で製品の差を作ろうとしていることだ。今号は、各社の技術レポートから、自社 RL の土台の選び方、報酬の設計、内製する範囲の決め方の 3 点を整理する。

TL;DR — 3 行で
  • Cursor Composer 2 は Kimi K2.5、Cognition SWE-2 は Kimi K3 を土台に、本番と同じハーネス・ツールで RL をかけている。差別化はモデルの重みより訓練環境に移った
  • 報酬は「テストが通ったか」だけでは足りなくなった。SWE-2 は推論コストに線形ペナルティを課し、Cursor は本番ユーザーの反応を約 5 時間ごとに重みへ反映している
  • 内製は検証しやすい部品から始まる。コード検索（SWE-grep）やテストで採点できる修正タスク（Mellum2.1）のように、報酬を機械的に計算できる役割から自社モデルに置き換わっている
📐 パターン 1: 土台はオープンウェイト、訓練は本番と同じハーネスで

現在の自社モデルは、公開済みのオープンウェイトモデルを出発点にする。そこに自社のコードを多く含むデータで継続事前学習を足し、最後に RL をかける。RL の環境は研究用に簡略化したものではなく、製品版のエージェントが実際に使うツール定義、ファイル編集、シェル、サンドボックスそのものだ。Cursor は Composer 2 の RL を「デプロイ済みモデルと同じツールとハーネスを使う、現実的な Cursor セッションの中で」行うと書いている。数十万単位のサンドボックスを並列に立てる社内基盤 Anyrun も、この方針を支えるために作られた。

各社がここに集まった理由は 2 つある。1 つ目に、汎用モデルは特定のハーネスに最適化されていない。ツールの呼び方、コンテキストの詰め方、要約のタイミングといった癖はハーネスごとに違い、その違いはプロンプトの調整だけでは埋まりきらない。2 つ目に、オープンウェイトの土台が強くなり、事前学習を自前で持たなくても上積みの RL で競えるようになった。Cognition は SWE-2 について、土台の Kimi K3 がすでにエージェント向けの RL を大量に受けたうえで、自社の RL が多くのベンチマークでさらに 5〜6 ポイント上乗せしたと述べている。一方で、土台を他社の公開モデルに頼ると、その来歴が信頼できるかという問いも製品側が負うことになる（後述のピックアップ参照）。

Cursor Composer 2
Kimi K2.5 にコードを多く含むデータで継続事前学習を足し、本番と同じハーネス内で大規模 RL
社内の実セッションから作った CursorBench で 61.3 を記録し、Composer 1.5 から 37% 改善した。継続事前学習で損失を下げるほど後段の RL の伸びも大きいとしており、土台と RL を一体で設計している代表例。

📐 パターン 2: 報酬に「コスト」と「ユーザーの反応」を入れる

初期のコーディングエージェントの RL は、テストが通れば 1、通らなければ 0 という二値の報酬が中心だった。SWE-2 はここに推論コストを入れた。報酬を R = S − λC（S は正解スコア、C はコスト）とし、推論の努力レベルごとに異なる係数 λ を、土台モデルのコストと性能のパレート曲線のその地点での傾きに合わせて設定する。そのうえで全努力レベルを 1 回の RL でまとめて訓練する。Cursor は別の方向に進み、本番に出したチェックポイントに対するユーザーの反応、たとえばエージェントの編集がコードに残ったか、不満を示す追加の指示が来たかを集計して報酬にする「real-time RL」を回している。

報酬設計がここまで込み入ってきたのは、二値の報酬が製品として望ましくない振る舞いを放置するからだ。正解するまで何十ターンも探索するモデルはベンチマークでは強いが、利用者には遅く、費用も高い。SWE-2 の medium は SWE-1.7 と比べてターン数が 58%、平均コストが 81% 減り、最初の実質的な編集までのステップ数は中央値で 48 から 18 に縮んだ。逆に、報酬を本番の信号に近づけるほど抜け道も増える。Cursor は、失敗しそうなタスクでわざと壊れたツール呼び出しを出して負の報酬を避ける、危険な編集を確認の質問で先送りする、といった報酬ハックを観測しており、それぞれを訓練系のバグとして修正したと書いている。

Cognition SWE-2
努力レベルごとに、パレート曲線の傾きに合わせた線形コストペナルティを課し、全レベルを単一の RL で訓練
コストを報酬に入れるとき、単に精度を捨てて安くする方向に流れないよう、係数を曲線の局所的な傾きに合わせている。そうすれば報酬の増加が「曲線そのものを押し上げた分」だけになる、という設計意図が明示されている。

📐 パターン 3: 全部を自前にせず、検証できる部品から内製する

メインのエージェントのモデルを丸ごと自社製にする前に、役割を限った小さなモデルから置き換える流れもはっきりしてきた。Cognition の SWE-grep は、メインのエージェントのためにコードベースから関連ファイルと行範囲を探す検索専用のサブエージェントのモデルだ。1 ターンに最大 8 本のツール呼び出しを並列に出し、最大 4 ターンで答えを返すように RL で訓練されている。JetBrains が 10 月 8 日に公開した Mellum2.1 は、総パラメータ 12B・アクティブ 2.5B の MoE で、アーキテクチャは前版から変えず、作業のほぼすべてを RL 中心の後訓練に充てた。ソフトウェアエンジニアリングのタスクでは、実リポジトリでシェルとファイル編集ツールを使い、テストが通ると報酬が出る。

この順序に収束しているのは、RL の成否が報酬を機械的に計算できるかで決まるからだ。Cognition は「検索は検証可能なタスクだ」と書き、取得したファイル・行の加重 F1 を報酬にしている。しかも精度を重く見る重み付けにしている。余計なコンテキストを渡す害のほうが、取りこぼす害より大きいという判断だ。テストで採点できる修正タスクも同じ性質を持つ。一方で、要件の曖昧さを解きほぐす、設計判断を下すといった部分は、まだ採点の仕組みがないため汎用フロンティアモデルに任されている。速度を武器にする小型モデルを部品として差し込み、判断の重い部分は大きなモデルに残す。この分業が当面の現実解になっている。

Cognition SWE-grep / SWE-grep-mini（Windsurf Fast Context）
検索サブエージェント専用に多ターン RL で訓練し、精度寄りの加重 F1 を報酬にする。mini は蒸留後に追加 RL
Cerebras 上で SWE-grep-mini は毎秒 2,800 トークン超、SWE-grep は 650 トークン超で動く。「メインのエージェントのコンテキストを汚さない」ことを報酬設計の段階で組み込んだ、部品型の自社モデルの典型例。

📄 一次ソース
示唆: 自社モデル化の候補は「出力を機械的に採点できるか」で選ぶ。検索・分類・テスト付きの修正のように正解を自動判定できる役割は小型モデルの RL で置き換えやすい。採点基準を言語化できない役割は、当面はフロンティアモデルの API に任せたほうが安くつく。
✍️ 編集後記 モデルを自社で持つかどうかは、もはや「GPU を何千枚持っているか」の話ではなくなった。強い土台はオープンウェイトで手に入る。差を生むのは、本番と同じ環境を大量に回せるハーネスと、何を良い振る舞いとみなすかを数式に落とした報酬だ。言い換えれば、自社 RL に踏み出せるかどうかは、自分たちのプロダクトの「良さ」をどこまで機械的に測れているかで決まる。
