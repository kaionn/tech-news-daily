今号のテーマ AGENT-INVENTORY

エージェントの台帳は「届け出」から「見つけて載せる」へ — 端末から検出する、他社基盤は同期で集める、ツール側から逆引きする

社内で動いているエージェントの一覧を正確に出せる組織はほとんどない。Copilot Studio や Agentforce で作られた業務エージェントは管理画面に残る。一方、開発者が手元で起動する Claude Code や GitHub Copilot CLI、各チームが AWS や Google Cloud で個別に立てたエージェントは、誰も届け出ないまま増えていく。11 月 17 日の Microsoft Ignite 2026 で Agent 365 は、端末上のローカルエージェント検出を GA にし、他社基盤のエージェントを同期で取り込む機能をプレビューで広げた。前日の 16 日には Okta が、CrowdStrike Falcon のセンサー経由で端末上のエージェントと MCP サーバーを見つける機能を説明している。同じ 17 日に GitHub は、Copilot のセッションの監査データを Agent 365 に流せるようにした。今号は、台帳への入口をどこに置くか、他社基盤のエージェントをどう集めるか、ツールから何を逆引きするかを各社の実装で並べる。

TL;DR — 3 行で
  • 台帳に載せる入口が、開発者や部門の届け出から、端末と通信の検出に移っている。Microsoft Defender は Claude Code や Copilot CLI を含む 60 種以上のローカルエージェントを検出し、端末と利用者に紐付ける（GA）。Okta は既存の CrowdStrike センサーを使い、OAuth 同意には現れないエージェントと MCP サーバーを拾う
  • 他社基盤のエージェントは、各基盤の管理画面を見て回るのではなく、一つの台帳への同期で集める。Agent 365 は対応基盤を一度接続すれば、エージェントのコードを変えずに登録簿へ同期する（プレビュー）。Okta も AWS Bedrock や Agentforce からの取り込みに対応した
  • 台帳はエージェントの一覧で終わらない。Agent 365 の tools registry（GA）は、エージェントが使うツールと MCP サーバーを集約し、遮断する前に依存しているエージェントを確認できる。GitHub は Copilot のプロンプト・応答・ツール呼び出しを監査ストリームとして台帳側へ送れるようにした
📐 パターン 1: 台帳への入口を届け出から検出に移す

これまでのエージェント管理は、管理者が作成を許可した場所、つまり Copilot Studio のようなノーコード基盤の管理画面に記録が残る前提で組まれていた。開発者が端末で claude や copilot を起動する場合、その前提は成り立たない。新しい構成では、すでに配備されている EDR やネットワーク経路からエージェントを見つける。Microsoft は Defender で管理下の Windows と macOS の端末を走査し、見つけたエージェントを端末と利用者に結び付けて登録簿に入れる。Global Secure Access は通信の側から、各エージェントが接続する宛先や MCP サーバーを見る。Okta は CrowdStrike Falcon のセンサーを情報源にし、専用の常駐ソフトを追加せずに端末上のエージェントと接続先の MCP サーバーを検出する。

入口が検出に移ったのは、ローカルエージェントの多くが、従来の SaaS 管理で使ってきた OAuth 同意の記録に現れないからだ。Okta は、ブラウザの外で動くエージェントは OAuth の同意からは見えないと書いている。CLI エージェントは開発者の資格情報でそのまま動くため、認可サーバーには利用者本人の操作としか記録されない。届け出制では、登録の手間をかけない人ほど台帳から漏れる。検出は、まず存在を把握してから所有者や制御を後付けする順番に入れ替える。Microsoft は 5 月の GA 時点では検出対象を OpenClaw から始め、Copilot CLI と Claude Code を予定としていた。11 月にはその 2 つを含む 60 種以上まで対象を広げている。

Microsoft Agent 365 + Defender / Global Secure Access
Defender が管理端末上のローカルエージェントを検出して端末・利用者と紐付け（GA）、Global Secure Access が宛先・MCP サーバーへの通信を可視化し、シャドー AI として登録簿に追加する（いずれもプレビュー）
Ignite 2026 の公式記事は、Defender と Global Secure Access が Claude Code や GitHub Copilot CLI を含む 60 種以上のローカル AI エージェントを検出すると明記している。検出後の制御も同じ記事で示されており、Windows 上ではエージェントループを検査して悪意ある指示を遮断するランタイム保護が GA、Intune によるファイル・ネットワーク境界の設定はプレビューとなっている。検出から制御までを一つの製品群で扱う構成の代表例だ。
📄 一次ソース
Okta for AI Agents（Shadow AI Agent Discovery for Endpoints）
既存の CrowdStrike Falcon センサーを情報源にして端末上のエージェントと MCP サーバーを検出し、Universal Directory に固有の ID で登録、認証済みの人間アカウントを所有者として紐付ける
11 月 16 日の公式ブログは、ブラウザの外で動くエージェントは OAuth の同意からは見えない、という理由で端末側の検出を足したと説明している。登録後は Agent Gateway がツール呼び出しごとにポリシーを適用し、異常があればキルスイッチで接続先へのアクセスを止める。所有者が異動・退職した場合やサブエージェントが生成された場合も、所有関係を追跡し続けるとしている。次の情報源として Okta Verify と他社 EDR を挙げており、現時点で検出元は CrowdStrike に限られる。
📄 一次ソース
示唆: 台帳づくりを利用申請フォームから始めない。まず EDR とプロキシのログから、どの端末で何のエージェントが動き、どこへ接続しているかを出す。届け出は、検出したエージェントに所有者を確定させる手続きとして後から付ける。
📐 パターン 2: 他社基盤のエージェントは同期で一つの台帳に集める

二つ目の流れは、他社基盤のエージェントを台帳へ同期することだ。エージェントは一つのクラウドに収まらない。営業部門は Agentforce、データ基盤チームは Databricks や Snowflake、開発チームは Bedrock や Vertex AI で作る。Agent 365 の connected platforms は、対応基盤を一度接続すれば、そこで作られたエージェントをエージェント側のコード変更なしに登録簿へ同期する。同期したエージェントには Microsoft Entra の Agent ID を発行し、他の ID と同じ条件付きアクセスやリスク評価の対象にする。接続時の認証にはワークロード ID フェデレーションを使い、長期間有効なシークレットを保存しない。

エージェントのコードに SDK を入れて自己申告させる方式を取らないのは、台帳の網羅性を各チームの実装に依存させないためだ。基盤側の API から一覧を取れば、登録を忘れたエージェントも、退職者が残していったエージェントも同じように拾える。Okta も Bedrock や Agentforce からの取り込みに対応しており、ID 管理側と生産性スイート側の双方が、自社を他社基盤の上位に置く集約点を狙っている。ただし同期できる情報は基盤によって差がある。Microsoft 自身も、機能は基盤ごとに異なり、Entra Agent ID の対応完了は 12 月だとしている。導入前には、どの基盤から何の属性が取れるかを確かめる必要がある。

Microsoft Agent 365（connected platforms / Entra Agent ID）
対応基盤を一度接続するとエージェントをコード変更なしで登録簿に同期し、Entra Agent ID を付与する。Salesforce Agentforce・Amazon AgentCore・Google Vertex AI への ID 対応を 12 月に完了予定（プレビュー）
5 月の GA 時点では、Bedrock と Google Cloud との同期は一覧の作成までで、起動・停止・削除といったライフサイクル操作は今後の予定とされていた。Ignite では同期対象を広げたうえで、非アクティブなエージェントや所有者のいないエージェントを洗い出す Action center を 12 月にプレビューで出すと発表した。一覧を作るだけでなく、棚卸しの作業まで台帳側で扱う方向に進んでいる。
📄 一次ソース
示唆: エージェント基盤を選ぶ際は、エージェントの一覧と所有者を API で外部に出せるかを確認項目に加える。管理画面でしか一覧を見られない基盤は、全社の台帳に入れられず、棚卸しのたびに人手で突き合わせることになる。
📐 パターン 3: ツールと活動記録から逆引きする

三つ目は、台帳の軸をエージェントだけでなくツールと活動記録にも広げる動きだ。Agent 365 の tools registry（GA）は、エージェントが使っているツールを一か所に集め、よく使われるものとリスクの高いものを示す。Azure AI Gateway や LiteLLM 経由の MCP サーバーも同じ画面で扱い（プレビュー）、管理者は MCP サーバーを遮断する前に、それに依存するエージェントやプラグインを確認できる。活動記録も台帳側に寄せられている。GitHub は 11 月 17 日から、Copilot のクラウドエージェント・CLI・VS Code・JetBrains などのクライアントの監査データを Agent 365 に流せるようにした。対象はセッションのプロンプト、応答、ツール呼び出しで、Enterprise Managed Users 構成の GitHub Enterprise Cloud に限られる。

逆引きが必要なのは、エージェントの危険度が、エージェントそのものより、どのツールにどの権限でつながっているかで決まるからだ。問題のある MCP サーバーが見つかったとき、エージェント単位の一覧しかなければ、影響を受けるエージェントを一つずつ調べることになる。ツール側から引ければ、遮断の影響範囲を先に把握できる。活動記録の集約も同じ理屈による。Microsoft の Dynamic agent risk（プレビュー）は、実行時のシグナルと接続範囲を合わせて、エージェントごとに一つのリスク水準を出す。製品の外にあるセッション記録が入ってこなければ、この評価は管理画面の設定値でしか計算できない。

GitHub Copilot → Microsoft Agent 365（監査ストリーミング）
Copilot の各クライアントでのセッション（プロンプト・応答・ツール呼び出し）を enterprise の監査ログストリーミングで Agent 365 に送り、Purview と Defender で調査に使う
11 月 17 日の GitHub Changelog によると、対象はクラウドエージェント、Copilot CLI、VS Code、Visual Studio、JetBrains や Eclipse などのパートナー IDE にまたがる。コーディングエージェントの提供元が、自社の管理画面に記録を閉じず、顧客の選んだ統制基盤へ活動記録を出している点が重要だ。仕組みは既存の監査ログストリーミングを使っており、新しい連携プロトコルを作っていない。
📄 一次ソース
示唆: 社内で MCP サーバーやツールを提供する側は、どのエージェントから呼ばれたかを記録しておく。台帳がエージェント側の一覧しか持たないと、ツールに問題が見つかったときに遮断の影響を事前に見積もれない。
✍️ 編集後記 エージェントの統制というと、何を許可するかを決めるポリシーの話になりやすい。今週の発表で各社が先に整えたのは、何が動いているかを数える仕組みだった。数えられないものには、ポリシーを書いても適用先がない。届け出を待たずに見つけ、所有者は後から確定させる。この順番に切り替えたことが、今回の変化の中心にある。
