今号のテーマ ASYNC-AGENTS

エージェントは「終わるまで待つ」をやめ始めた — 窓口と作業者を分ける、ツール結果は後から返す、走っている作業に指示を足す

エージェントに頼む仕事が「質問に答える」から「調べて、書いて、確かめる」へ広がるにつれ、1 本の ReAct ループの弱点がはっきりしてきた。長いツール呼び出しが 1 つ入るとループ全体が止まり、その間ユーザーは話しかけられず、ほかの仕事も後ろに並ぶ。LangChain は 11 月 5 日の記事「Agents Are Going Async」で、ユーザーと話すオーケストレーター 1 体と、裏で長い作業を進めるワーカー群という構成に業界が収束しつつあると書いた。Claude Code はサブエージェントを既定でバックグラウンド起動し、OpenAI はモデル API に非同期ツール呼び出しを入れ、常時稼働型の dots は作業を背景のエージェントに渡す。今号は、各社が「待たないエージェント」をどの層で実装し、結果の受け取りと途中の指示変更をどう設計したかを並べる。

TL;DR — 3 行で
  • 会話の窓口と長い作業を別のループに分ける構成が標準になりつつある。LangChain Deep Agents は起動した瞬間にタスク ID を返す 5 つのツールを持ち、Claude Code はサブエージェントを既定でバックグラウンドで走らせる
  • 非同期はモデル API の層にも降りてきた。OpenAI の async tool calling ではツールに async: true を付けるとモデルが結果を待たずに先へ進み、アプリは後から call_id を合わせて結果を返す
  • 走っている作業への指示変更と承認の経路が新しい設計対象になった。Deep Agents は「中断して再実行」か「後ろに積む」かを選ばせ、承認待ちはサブエージェント側のスレッドで答える。dots は Activity 画面で委任先の作業を個別に止められる
📐 パターン 1: 会話の窓口と長い作業を別のループに分ける

非同期エージェントの基本形は、ユーザーと話すオーケストレーターが長い作業をサブエージェントに渡し、完了を待たずに会話へ戻る構成だ。LangChain Deep Agents の async subagents では、オーケストレーターが start_async_task・check_async_task・update_async_task・cancel_async_task・list_async_tasks の 5 つのツールを持つ。start_async_task はサブエージェントを独立したスレッドで起動してすぐに返り、タスク ID はそのままスレッド ID になる。Claude Code も、何も設定しなければメイン会話から起動されたサブエージェントはバックグラウンドで始まり、結果は後のターンに「完了通知」として届く。通知はユーザーの発言ではなく自動イベントとして区別され、進捗を聞かれた時点で終わっていなければ「まだ実行中」と答える。

この形に収束した理由は、応答性と処理量を 1 本のループで両立できないからだ。同期型のループでは、10 分かかる調査を走らせればその 10 分はユーザーの訂正も受け付けられない。ループを分ければ、窓口は常に空いていて、処理量はループの長さではなくワーカーの数で決まる。その代わり、タスクの状態を会話履歴とは別に持つ必要が出てくる。Deep Agents はタスクのメタデータを async_tasks という専用の state チャネルに置き、履歴が要約されても未完了タスクを見失わないようにしている。Claude Code は同時実行数を既定で 20 に制限し、超えると Concurrent subagent limit reached で起動を失敗させる。ワーカーを増やせることと、増やしすぎを止めることが同じ設計の中に入っている。

LangChain Deep Agents（async subagents）
オーケストレーターに起動・確認・更新・取消・一覧の 5 ツールを持たせ、各サブエージェントを独立スレッドで走らせる
11 月 5 日の公式ブログでは、Claude Code の背景サブエージェント、OpenAI dots、DeepSeek Harness のルーターを例に、業界が「1 体の窓口 + 背景ワーカー」に収束していると整理した。公式ドキュメントによると、サブエージェントは Agent Protocol サーバー上で動き、同一デプロイ内に置くか別サーバーに分けるかを選べる。通知と update_strategy は beta で、API は変わる可能性がある

Claude Code（バックグラウンドサブエージェント）
サブエージェントを既定でバックグラウンド起動し、結果を完了通知として後のターンで受け取る
公式ドキュメントによれば、バックグラウンドのサブエージェントは前面実行より小さい組み込みツールセットで動き、同時実行数は CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS（既定 20）で制限される。API エラーで失敗した場合も最後の出力を通知に含め、途中までの成果が失われないようにしている。待たせたい場合は CLAUDE_CODE_FORK_SUBAGENT=0 などの設定で同期実行に戻せる
📄 一次ソース
示唆: 長い作業を持つエージェントを作るなら、窓口のループと作業のループを最初から分け、タスクの状態（ID・状態・開始時刻）は会話履歴とは別の場所に保存する。同時実行数の上限も同じタイミングで決めておく。履歴の中だけでタスクを管理すると、要約や圧縮のたびに未完了の仕事を見失う。
📐 パターン 2: ツール結果を後から返す — 非同期をモデル API の層に下ろす

サブエージェントの非同期化はフレームワーク側の工夫だが、OpenAI は同じ考え方を Responses API のツール呼び出しに入れた。関数ツールかカスタムツールの定義に "async": true を付けると、モデルはそのツールを結果待ちが要らない呼び出しとして扱う。function_call を出したあとも、依存しない部分の回答を同じレスポンスの中で続ける。アプリケーションはジョブを自前で走らせ、終わったら previous_response_id に最新のレスポンス ID を入れた新しいリクエストを送り、元の call_id に合わせた function_call_output を返す。ガイドには、async tool は実行を OpenAI 側に移すものでも、バックグラウンドジョブを管理するものでもないと明記されている。

ここで決まっているのは役割の分担だ。モデルは「どの結果が先に必要か」を判断し、ジョブの実行・保持・再試行はアプリの責任のまま残る。次の手順が保留中の結果に依存する場合は、アプリ側で wait_for_tasks のような同期ツールを定義し、モデルにそれを呼ばせて待たせる。ユーザーへの質問も非同期ツールとして定義できるが、レスポンスは回答を待って開いたままにはならないので、答えが必要な手順の前で待つようモデルに指示する必要がある。制約もはっきりしている。対象はアプリが実行する関数ツールとカスタムツールに限られ、ホスト型の組み込みツールは含まれない。Multi-agent モードでは並列ツール呼び出しと組み合わせられず、タスクハンドルは完了済みのものも含めて会話全体で一意にしなければならない。非同期をモデルに任せるほど、ID の対応付けの正しさはアプリ側で保証することになる。

OpenAI Responses API（async tool calling）
ツール定義に async: true を付けるとモデルが結果を待たずに進み、アプリは後のリクエストで call_id を合わせて結果を返す
公式ガイドでは、レスポンス生成そのものを非同期にする Background mode とは別の機能と位置付けている。待機用ツール（wait_for_tasks）やユーザー入力用ツール（request_user_input_async）は組み込みではなく、アプリ側で定義するパターンとして示されている。対応モデルは GPT-6 Astra 以降
📄 一次ソース
示唆: モデル API の非同期ツールを使う場合、ジョブの実行キュー・タスクハンドルと call_id の対応表・タイムアウト時に返す「結果なし」の扱いは、すべて自分のアプリで持つ前提で設計する。API が非同期に対応しても、ジョブ管理まで肩代わりしてくれるわけではない。
📐 パターン 3: 走っている作業への指示と承認をどこで受けるか

作業を裏に回すと、同期型では起きなかった問いが 2 つ出てくる。実行中のタスクに新しい指示が来たらどうするか。タスクが承認を求めたとき、誰がどこで答えるか。Deep Agents は update_async_task に update_strategy を持たせ、既定の "interrupt" は現在の実行を止めて新しい指示で再実行し、"enqueue" は今の実行が終わるまで指示を積んでおく。前者は方向の訂正に、後者は追加の依頼に向く。承認が必要になったサブエージェントは waiting 状態になり、ユーザーはオーケストレーターではなくサブエージェント自身のスレッドで答える。Slack 上の Managed Deep Agents では、承認の依頼が元のスレッドに投稿され、そこへの返信で再開する。Claude Code は逆に、バックグラウンドのサブエージェントの権限確認をメインのセッションに出し、どのサブエージェントからの依頼かを名前で示す。

承認をどこに出すかで設計が分かれているのは、何を守るかの優先順位が違うからだ。Deep Agents は窓口の会話を承認待ちで止めないことを優先し、承認を作業側のスレッドに閉じ込めた。Claude Code は承認を 1 か所に集め、ユーザーが見落とさないことを優先した。その分、セッション全体に及ぶ許可を 1 回与えると、メイン会話にも同じ許可が適用される。OpenAI dots はさらに、どの種類の更新をどのチャネル（ChatGPT・Slack・Teams）に送るかをユーザーが決められる。Activity 画面では、メインのタスクの一時停止と、委任先のタスクや定期タスクの停止・取消を別々に操作できる。共通しているのは、止めても取り消せないという前提だ。dots のドキュメントは、タスクを止めても完了済みの操作は元に戻らないと明記し、Deep Agents も取消は実行中の run を止めるだけである。

OpenAI dots（常時稼働エージェント）
背景のエージェントや Codex タスクに作業を渡し、通知チャネルの振り分けと委任先ごとの停止を利用者に持たせる
公式ドキュメントによると、dots は専用のクラウド上のコンピューターとブラウザで動くため、ユーザーの端末がオフでも作業が続く。作業中も話しかけて新しい情報や優先順位を渡せ、作業を最初からやり直す必要はない。アカウントに影響する操作や情報共有の前には自動の承認チェックが入り、進めるか、承認を求めるか、ユーザーに引き渡すかを判定する。Pro と Business Premium の対象アカウントに段階的に展開している
📄 一次ソース
LangChain Deep Agents（update_strategy と waiting 状態）
実行中タスクへの追加指示を interrupt / enqueue で選ばせ、承認待ちはサブエージェントのスレッドで解決する
公式ドキュメントには端のケースまで書かれている。enqueue で積んだ指示は、開始前に現在の実行が一時停止すると破棄される。waiting 中のタスクを更新すると保留中の承認依頼は消え、取消は状態を cancelled にするだけになる。アイドル中のオーケストレーターを起こすのは完了か失敗の通知だけで、承認待ちでは起こさない
📄 一次ソース
示唆: 背景タスクを持つエージェントでは、「実行中に指示が来たら止めるか積むか」と「承認依頼を窓口に集めるか作業側に置くか」を仕様として先に決め、UI で見分けられるようにする。どちらにしても、停止は完了済みの操作を戻さないことをユーザーに見える形で伝える。
✍️ 編集後記 非同期化で一番難しいのは並列実行そのものより、「いま何が走っていて、誰の返事を待っているか」を窓口が正しく把握し続けることだと各社の設計から読み取れる。タスクの状態を会話の外に保存すること、承認の行き先を決めること、止めても戻らないと明示すること。どれも従来のジョブキュー設計で使われてきた答えで、エージェントはそれを会話の中に持ち込み始めたところだ。
