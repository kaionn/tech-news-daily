今号のテーマ MEMORY-HYGIENE

エージェントの記憶は「溜める」から「手入れする」へ — 読む時に根拠を確かめる、棚卸しはセッションの外で、共有ファイルは PR で直す

コーディングエージェントのメモリと指示ファイルは、この 1 年で「あるのが当たり前」になった。そのぶん次の問題がはっきりしてきた。書いた時点では正しかった記述が、リファクタやフレームワークの置き換えで静かに古くなり、エージェントはそれを自信を持って守り続ける。10 月 28 日、GitHub は Copilot Memory の GA と同時に、過去の作業を振り返ってメモリと AGENTS.md / CLAUDE.md などを整理する「Copilot Dreaming」をパブリックプレビューで出した。OpenAI Codex も Claude Code も、記憶を「どう保存するか」より「古くなったものをどう見つけて直すか」に仕組みを足している。今号は、各社が記憶の手入れをどこで・誰の権限で行うようにしたかを並べる。

TL;DR — 3 行で
  • 記憶の正しさは書いた時点では決まらない。GitHub はメモリにコード位置の引用を付け、読み出す時にエージェントが根拠を確かめる方式を採った
  • 古い記憶の整理は会話の外で走らせる流れになった。Copilot Dreaming と Codex はいずれもバックグラウンドで処理し、Codex は作業中の会話を避けるためアイドルになるまで待つ
  • 直してよい範囲は変更対象で分ける。Copilot Dreaming はメモリを直接書き換え、リポジトリに置かれた指示ファイルは PR で提案する。Claude Code の指示監査は報告だけでファイルを変えない
📐 パターン 1: 書いた時点の正しさを信じない — 読み出す時に根拠を確かめる

メモリの陳腐化に対する最初の答えは、記憶そのものに「根拠の場所」を持たせ、使う直前に照合することだ。GitHub Copilot のメモリは、各事実を裏付けるコード位置への参照（citation）付きで保存される。エージェントは記憶を読み出すたびに参照先のコードを確かめ、コードと食い違っていたり参照先が存在しなかったりすれば、新しい証拠に基づく修正版を書き直す。古い記憶を消す専用の仕組みを持たず、「使われる記憶ほど検証される」状態を作って誤りを自己修復させる設計である。

この方式が選ばれたのは、陳腐化の原因が記憶の外、つまりコードの変更にあるからだ。src/legacy/ を消すリファクタが入った時点で、それに触れた記憶はすべて怪しくなる。しかし書き込み側はその変更を知らない。記録したエージェントではなく現在のコードを正とし、照合のコストを実際に読まれる記憶だけに払う。ここでの割り切りは、全件を定期的に洗い直すよりも安く、しかも外れた記憶を確実に拾える点にある。

GitHub Copilot Memory（citation 付きメモリ）
メモリをコード位置の引用付きで保存し、読み出し時にエージェントが引用先を検証して食い違えば修正版を保存する
2026 年 1 月の GitHub 公式エンジニアリング記事。コードと矛盾する記憶と無関係な引用を意図的に仕込んだ検証で、エージェントが引用を確かめて矛盾を見つけ、記憶を更新したと報告している。A/B テストでは coding agent の PR マージ率が 83% から 90% に上がった。オフラインの整理サービスは、GitHub の規模では実装の複雑さと LLM コストが大きく、しかも読み出し時の突き合わせも結局必要になるとして見送った経緯も書かれている
📄 一次ソース
示唆: 自前でエージェントのメモリを作るなら、記憶 1 件ごとに根拠（ファイルパス・行・コミット）を持たせ、読み出し時に照合して食い違えば書き直すことから始める。根拠を持たない記憶は、正しいかどうかを後から判定する手がかりがない。
📐 パターン 2: 棚卸しはセッションの外で走らせる

読み出し時の検証では拾えないものもある。一度も読まれずに残り続ける重複、互いに矛盾する指示、別のフレームワーク向けに書かれたままの指示ファイルなどだ。そこで各社は、会話中のエージェントとは別に、過去のセッションを振り返って記憶を統合・削除する処理をバックグラウンドで持ち始めた。GitHub は 10 月 28 日に Copilot Dreaming をパブリックプレビューで公開した。対象は個人メモリ、リポジトリの設定（指示ファイル・スキル）、コードレビュー用ガイダンスの 3 種で、会話を開いていなくても動く。OpenAI Codex のメモリも会話終了の直後ではなくバックグラウンドで更新し、作業途中の内容を要約しないように、会話が十分アイドルになるまで待つ。

会話の外に出す理由は 2 つある。1 つは対象の性質だ。作業中のセッションは結論が固まっておらず、ここから記憶を作ると途中の思い込みまで残る。もう 1 つはコストの切り分けである。整理処理はトークンを使うので、ユーザーの操作待ちと切り離し、量と頻度を別に制御したい。Copilot Dreaming は変更がなかった実行や非アクティブなリポジトリでも AI クレジットを消費すると明記し、先に支出上限を設定するよう求めている。Codex はレート制限の残量が閾値を下回ると処理を飛ばす設定を持つ。1 月に GitHub が「オフライン整理はコストが高い」として見送った処理が、10 月にオプトインかつユーザー課金の機能として出てきた形で、整理のコストを誰が負担するかが製品設計の論点になった。

GitHub Copilot Dreaming（パブリックプレビュー）
同期済みセッションと PR レビューのフィードバックを分析し、古いガイダンスの修正と重複メモリの削除をバックグラウンドで行う
公式ドキュメントによれば、変更するのはコンテキストであって基盤モデルではない。オプトイン方式で、組織ポリシーか個人設定で有効にする。実行ごとに AI クレジットを消費し、無効化しても過去の変更の取り消しや、削除済みメモリの復元は行われない

OpenAI Codex（Memories）
過去の会話からローカルのメモリファイルを作る処理を、会話がアイドルになってからバックグラウンドで実行する
公式ドキュメントでは、進行中や短時間のセッションを対象外にし、生成時にシークレットをマスクする。抽出と全体統合（consolidation）でモデルを別々に指定でき、レート制限の残量が閾値を下回れば処理をスキップする。記憶の作成と統合を別工程にした構成がそのまま設定項目に表れている
📄 一次ソース
示唆: 記憶の整理処理を入れるなら、対象は「アイドルになった・閉じた」セッションに限り、実行頻度と予算の上限を整理処理とは別の設定として持たせる。会話中のエージェントに整理まで任せると、作業途中の推測が記憶に混ざり、コストも作業本体と区別できなくなる。
📐 パターン 3: 直してよい範囲を変更対象で分ける

記憶の手入れで各社の設計が最も揃っているのは、権限の切り分けだ。エージェントが自分のために持つメモリは自動で追加・更新・削除してよい。一方、チームで共有しリポジトリに置かれた指示ファイルは、人間のレビューを通してしか変えない。Copilot Dreaming はメモリを変更ごとの承認なしで更新するが、AGENTS.md・CLAUDE.md・.github/copilot-instructions.md・.github/skills/** などへの変更は PR として提案し、マージされるまでファイルは変わらない。Claude Code の /doctor prompt-audit はさらに慎重で、古いモデル向けの指示、存在しないファイルやコマンドへの参照、ファイル間の矛盾を洗い出して修正案付きのレポートを返すが、ユーザーが頼むまで何も書き換えない。

この線引きは、記憶と指示の役割の違いから来ている。Codex のドキュメントは、必ず守らせたいチームの方針は AGENTS.md やリポジトリ内の文書に書き、メモリは「便利な想起の層」として扱って、常に適用すべきルールの唯一の置き場にしないよう明記している。メモリが間違っても影響は 1 人のセッションの効率にとどまる。指示ファイルが間違えば、チーム全員のエージェントが同じ誤りを繰り返す。影響範囲が大きいものほど自動書き換えから遠ざける、という順序付けである。Claude Code は自動メモリにも書き込み時の制約を課している。MEMORY.md はセッション開始時に先頭 200 行または 25KB までしか読み込まれず、上限に近づくと 1 行 1 項目に保ち古い項目を統合・削除するよう促し、超えた場合は索引を書き直すようエラーを返す。

Claude Code（/doctor prompt-audit と自動メモリの上限）
指示ファイルの陳腐化・矛盾は修正案付きレポートで返すだけで、自動メモリは読み込み上限で肥大化を止める
公式ドキュメントは、矛盾する指示があると Claude がどちらかを任意に選ぶ可能性があるとして、CLAUDE.md と .claude/rules/ の定期的な見直しを勧めている。その見直しを機械に手伝わせる一方、書き換えの判断は人に残す設計になっている。自動メモリ側は、書き込み直後にサイズを測って整理を促す「書き込み時の手入れ」を担う

GitHub Copilot Dreaming（変更経路の分離）
メモリとコードレビュー用ガイダンスは直接更新し、リポジトリに置かれた指示・スキルの変更は PR で提案する
10 月 28 日の公式 changelog は、Dreaming の種類を個人メモリの整理・リポジトリのカスタマイズ・コードレビューのカスタマイズの 3 つに分けている。そのうえで、メモリは追加・更新・削除できる一方、リポジトリに置かれたスキルと指示への変更は「チームがレビューする PR として提案される」と明記する。共有ファイルの陳腐化は自動で見つけ、反映は既存のコードレビューの流れに乗せる形である
📄 一次ソース
示唆: 自動整理を入れる前に、書き換え対象を「個人・エージェント専用の記憶」と「チームで共有する指示」に分け、後者は必ず PR かレポート経由にする。消去は特に慎重に扱い、少なくとも共有物は自動で消さない。必ず守らせたいルールはメモリではなく、レビューを通るファイルに置く。
✍️ 編集後記 記憶を持つエージェントの品質は、どれだけ覚えたかより、どれだけ古いものを捨てられたかで決まり始めている。読み出し時の検証、セッション外での棚卸し、共有ファイルの PR 経由の修正は、それぞれ別の種類の陳腐化に対応する。3 つは代替ではなく組み合わせる前提で考えたほうがよい。気がかりなのは、Dreaming のような整理処理自体が AI の判断で記憶を消す点だ。「整合している」ことと「正しい」ことは別なので、何を消したかを後から追える記録が次の論点になるとみている。
🔗 今号の動向ピックアップ
TEPA: 矛盾する新しい証拠で古い記憶を「失効」させる観測をキー付きの前例として保存し、同じキーで矛盾する証拠が来たら前例を失効させる（監査用に履歴は残す）手法。追記のみのメモリは状況が完全に反転すると 0.21 まで落ち、メモリなし（0.31）を下回った。本号第 1 節の「書いた時点の正しさを信じない」を定量的に裏付ける結果だ。
DreamBench-SWE: 複数セッションにまたがる記憶衛生のベンチマーク前のセッションの証拠に依存する後続タスクを、隠しテストで採点するソフトウェアエージェント向けベンチマーク。メモリありの条件はいずれもメモリなし（21/180）を有意に上回ったが、整理方式どうしの優劣は示せなかったと著者自身が書いている。棚卸し処理の効果を測る方法は、まだ固まっていない。
agent-memory: 無人の整理処理は追加と更新まで、削除は人の承認待ちMarkdown を正本とし、Claude Code と Codex で同じ記憶ストアを共有する OSS のメモリランタイム。スリープ時の整理パスは記憶の追加・更新はできるが、削除は必ず提案として出して人が確定する。本号第 3 節の「直してよい範囲を分ける」を、削除という操作の単位で実装した例である。
