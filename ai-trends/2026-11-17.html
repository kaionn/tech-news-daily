今号のテーマ CREDENTIAL-ISOLATION

エージェントに秘密を渡さない設計へ — 資格情報はサンドボックスの外で付ける、宛先に縛る、届かない経路は先に洗い出す

サンドボックスはエージェントが動かすコードをホストから隔離する。それでも、API キーを環境変数で渡していれば、隔離された中で printenv を叩くだけで読めてしまう。プロンプトインジェクションで「この値を外部に送れ」と指示されたら、キーはそのまま外に出る。そこで 2026 年後半の実行基盤は、サンドボックスの中に本物の秘密を置かない構成に揃い始めた。11 月 12 日に Anthropic が private beta で公開した self-hosted Claude Managed Agents は、資格情報をサンドボックス外のプロキシで付与する構成をそのまま顧客環境に持ち込める。Docker Sandboxes（sbx）は 11 月の 2 回のリリースで、秘密の差し替え先を宛先ホストに限定する変更を入れた。今号は、秘密をどこで付けるか、どの宛先に縛るか、プロキシが届かない経路をどう扱うかを各社の実装で並べる。

TL;DR — 3 行で
  • 本物の資格情報をサンドボックスの外のプロキシに持たせ、外向きリクエストに付与する構成が実行基盤の標準になりつつある。中のエージェントが見るのは proxy-managed のようなプレースホルダだけで、環境変数を読まれても漏れるのは偽の値になる
  • 付与する宛先は秘密ごとに固定する。Docker sbx 0.51.0 は宛先ホストを持たないカスタムシークレットの差し替えを止め、Cloudflare Sandboxes は allowedHosts を設定すると既定拒否に切り替わる。宛先を縛らないプロキシは、どこへでも本物のキーを付けて送る中継器になる
  • プロキシで守れる範囲には限りがある。Anthropic は対象を MCP ツールと対応 API 呼び出しに限っていると明記し、それ以外のサービスは本番前に確認するよう求めている。Blaxel は、任意のコードはプロキシ設定の環境変数を無視できるため、直接接続を塞ぐネットワーク境界が別に要ると書いている
📐 パターン 1: 資格情報はサンドボックスの外で付ける

構成の要点は、エージェントのコードが動く場所と本物の秘密がある場所を分けることだ。サンドボックスの外向き通信はすべてホスト側か基盤側のプロキシを通る。プロキシは宛先を見て対応する資格情報を引き、Authorization などの認証ヘッダーを書き換えてから転送する。サンドボックスの中では、環境変数にもファイルにも本物の値はない。Docker sbx の場合、エージェントが見る値は proxy-managed という番兵文字列で、カスタムシークレットでは sbx-cs-<rand> 形式になる。OAuth もホスト側でサインインするため、トークンはサンドボックスに入らない。エージェントのコードやツールは、キーが入っている前提で普通に HTTP を呼べばよく、書き換えは要らない。

この形に収束したのは、プロンプトインジェクションへの対策を「モデルが騙されないこと」に頼れないからだ。エージェントは読んだ Web ページや Issue の文面に従ってシェルを叩くことがあり、サンドボックスはそのコードを止めない。止めるのはホストへの侵入であって、中にある値の持ち出しではない。秘密を最初から中に置かなければ、指示に従って printenv を実行されても、送り出されるのは偽の値で済む。環境変数で渡す方式は、秘密をモデルのコンテキストからは外せても、サンドボックス内のプロセスからは外せない。各社がプロキシ方式に寄せているのはこの差による。

Claude Managed Agents（self-hosted、private beta）
エージェントループ・セッション履歴・vault の秘密をサンドボックスの外に置き、MCP ツールと対応 API 呼び出しには外部プロキシが資格情報を付ける。self-hosted では顧客自身のシークレットマネージャーに秘密を置ける
11 月 12 日の公式記事によると、ハーネス（モデルを呼ぶ側）とサンドボックス（コードを実行する側）は設計上分離されており、サンドボックスはツールが必要になった時点で起動する。self-hosted 版では Managed Agents サーバー、セッション履歴を持つデータベース、シェルとファイル操作を実行するワーカーを顧客が自分のクラウドかオンプレミスで運用する。モデル本体は引き続き Anthropic 側（または Bedrock などのクラウド、顧客のゲートウェイ経由）で動く

Docker Sandboxes（sbx）
ホスト側の HTTP/HTTPS プロキシが外向きリクエストを横取りし、宛先に対応する資格情報を OS のキーチェーンから引いて認証ヘッダーを上書きする
公式ドキュメントによると、秘密は macOS Keychain・Windows Credential Manager・Linux Secret Service に保存され、1Password や AWS Secrets Manager を参照する設定もできる。参照先の値はホスト側で解決し、既定で 55 分キャッシュする。Git 操作には SSH エージェント転送を使い、秘密鍵はホストに残る。ただし kit が passthrough: true を指定すると本物の OAuth トークンがサンドボックスに入り、隔離が弱まることもドキュメント自身が明記している
📄 一次ソース
示唆: エージェント実行環境を棚卸しするときは、まずサンドボックス内で env を実行し、本物の API キーが見えるかを確かめる。見えるなら、隔離の強さに関係なく、プロンプトインジェクション一回で持ち出される状態にある。プロキシ方式への移行は、アプリのコードを変えずに環境変数の値を番兵に置き換えるところから始められる。
📐 パターン 2: 秘密は宛先ホストに縛る

プロキシに秘密を預けただけでは足りない。どの宛先へのリクエストにその秘密を付けるかを決めていなければ、プロキシは攻撃者のサーバーへのリクエストにも本物のキーを付けて送ってしまう。そこで各社とも、秘密と宛先ホストを一対一か一対多で結び付けて登録させる。Docker sbx は組み込みの 11 サービス（anthropic、github、openai など）ごとに注入先ドメインを固定し、それ以外のドメインには付けない。たとえば組み込みの github は npm.pkg.github.com には付かないので、GitHub Packages から private パッケージを取るには、そのホスト用のカスタムシークレットを別に登録する。Cloudflare Sandboxes では outboundByHost にホストごとのハンドラを書き、その中でヘッダーを付ける。ctx.containerId を使えばインスタンスごとに違う資格情報を割り当てられる。

宛先を縛る仕組みは、外向き通信の許可リストと同じ層に置かれるようになった。Cloudflare では allowedHosts を設定した時点で既定拒否になる。setOutboundHandler() を使えば、再起動なしでインスタンスごとに方針を切り替えられる。npm install の間だけ通信を開け、その後は 403 を返すハンドラに替える使い方も例示されている。Docker sbx は 11 月 3 日の 0.51.0 で、宛先ホストを持たないカスタムシークレットの差し替えを止めた。既存の設定は宛先ホストを明示すれば直る。「どこに付けるか」を書かない秘密は使えない、という既定への変更だ。資格情報の管理と通信の許可を別の設定ファイルで持つと、片方だけ緩む隙間ができる。両者を同じ宛先リストで管理する方向に寄っているのはそのためだと考えられる。

Cloudflare Sandboxes（Outbound Workers）
外向き通信を Workers ランタイム上のハンドラで処理し、ホスト単位で資格情報を付ける。allowedHosts / deniedHosts と実行時のハンドラ差し替えで、インスタンスごとの通信方針を持つ
公式の changelog によると、ハンドラはサンドボックスの外の Workers ランタイムで動くため、サンドボックスからは見えない秘密を保持できる。Worker 環境の秘密をローテーションすると次のリクエストから反映される。HTTPS を中継するため、インスタンスごとに使い捨ての CA を用意し、その秘密鍵はコンテナランタイムのサイドカープロセスの外に出さない。インスタンス間で鍵は共有しない

Docker Sandboxes 0.51.0 / 0.53.0
宛先ホストを持たないカスタムシークレットは差し替えない既定に変更（11 月 3 日）。11 月 11 日の 0.53.0 では Claude Code の Remote Control でも環境とセッションの資格情報をホストに残す
リリースノートによると、0.51.0 では標準入力から秘密を読む --value-stdin も追加され、値がコマンド引数やシェル履歴に残らなくなった。ポリシー一覧では暗黙の既定拒否を明示的な拒否ルールと区別して表示するようになった。sbx policy は空の --sandbox 指定を拒否し、全サンドボックスへ誤って適用されるのを防ぐ。10 月 26 日の 0.50.0 では、MCP の OAuth リクエストで別オリジンへの資格情報リダイレクトを遮断している
📄 一次ソース
示唆: 秘密を登録するときは、値と一緒に「付けてよい宛先ホスト」を必ず書く。宛先が空でも動く設定は、プロキシを経由した持ち出し経路になる。外向き通信の許可リストと資格情報の宛先リストは別々に管理せず、同じ一覧から両方を作るほうが、片方だけ緩む事故を防ぎやすい。
📐 パターン 3: プロキシが届かない経路を先に洗い出す

プロキシ方式は、通信がプロキシを通ることを前提にしている。多くの実装は HTTPS_PROXY などの環境変数でクライアントを向けるが、エージェントが書いた任意のコードはそれを無視して直接接続できる。Blaxel はこの点を明記し、プロキシ経由の通信に対するドメインフィルタとは別に、直接接続を塞ぐネットワーク境界が要るとしている。差し替えの範囲にも限りがある。Docker sbx のカスタムシークレットは HTTP ヘッダーだけを置き換え、リクエストボディ内のプレースホルダは置き換えない。Linux でキーチェーンがない環境では、秘密は権限 0700 のファイルに保存される。そのファイルを読めるユーザーやプロセスからは取り出せる、とドキュメント自身が書いている。

各社がこうした制限を製品ページで先に開示しているのは、プロキシ方式が「入れれば全部守られる」仕組みではないからだ。Anthropic の self-hosted 版の記事も、プロキシで守るのは MCP ツールと対応 API 呼び出しだけだと書いている。エージェントが使う他のサービスは本番投入前に確認するよう求め、許可リストの設定と運用は顧客のファイアウォール側の責任だとしている。秘密の置き場所もプロキシ自体も、実行基盤から切り出して独立に運用できるようになった。Infisical の Agent Proxy は CLI に同梱されてローカルで動くほか、Docker コンテナとして別ホストに置き、ネットワーク上の複数エージェントに共有させる構成も選べる。移行の際は、守られる経路の一覧より先に、守られない経路の一覧を作るほうが確かだ。

Blaxel（サンドボックス）
{{SECRET:name}} で参照する秘密をプロキシのルーティングルールの destinations に結び付けて注入する。秘密は暗号化保存の書き込み専用で、API レスポンスで返さない
10 月 7 日の公式ブログによると、Stripe 用の鍵は OpenAI へのリクエストには付かないよう、スコープをルール単位で持つ。一方で、ドメインフィルタはプロキシ経由の通信にしか効かず、プロキシの環境変数を守るツールが前提だと認めている。任意のコードはその変数を無視できるため、完全に強制するには直接接続を遮断する別のネットワーク境界が要るとしている
📄 一次ソース
Infisical Agent Proxy
エージェントとプロキシに別々のマシン ID を割り当て、プロキシ対象サービスごとにホスト名・認証方式・付与する秘密を定義する独立した資格情報ブローカー
公式ブログによると、Infisical CLI に同梱されるほか Docker コンテナとしても配布され、サイドカーや共有プライベートネットワーク上など、エージェントに近い別ホストに置く構成を推奨している。静的な秘密に加えて動的シークレットも扱え、監査ログ・RBAC・ローテーションは Infisical 本体の機能を引き継ぐ。前身はオープンソースの Agent Vault
📄 一次ソース
示唆: プロキシ方式を入れる前に、エージェントが通信する先を全部書き出し、それぞれ「プロキシ経由で付与」「付与なしで許可」「遮断」のどれにするかを決める。どれにも入らない経路があれば、直接接続を塞ぐネットワーク境界が揃うまで、その経路の資格情報は環境変数で渡さない。
✍️ 編集後記 サンドボックスの議論は長く「どれだけ強く閉じ込めるか」だったが、今号の各社の実装が扱っているのは「閉じ込めた中に何を置かないか」だ。隔離の強さを上げても中に本物のキーがあれば意味は薄く、逆にキーを外に出せば、隔離が多少弱くても一度の注入で失うものは小さくなる。次に問われるのは、プロキシを経由して正当に付与された権限そのものをどこまで狭く切れるかだろう。
