今号のテーマ GOAL-DIRECTED-AGENTS

長く走るエージェントには「タスク」ではなく「目標と合格条件」を渡す — 成功の定義と予算を先に決める、完了の判定は作業者の外に置く、人が見るのは判断だけに絞る

11 月 17 日、Replit は Missions を、Cognition は Devin Bots を同じ日に発表した。Microsoft の Autopilot も同日から Frontier 顧客への展開が始まっている。三つとも数時間から数週間動き続け、人が切り出したタスクではなく目標を受け取って、自分で計画し作業を割り振る。依頼の単位がここまで大きくなると、プロンプトの書き方より、何をもって完了とするか、いくらまで使うか、どの行為の前に人へ確認するかという取り決めが重くなる。今号はこの 3 点を、19 日に公開ベータになった Databricks Genie ZeroOps も加えて各社の実装で比べる。

TL;DR — 3 行で
  • 依頼の単位が「タスク」から「目標＋成功条件＋予算＋境界」の取り決めに変わった。Replit Missions は開始時の質問で成功の定義を詰め、上限金額と許容するトレードオフを合意してから動き、予算が尽きたら未達のまま止まる。Devin Bots は「変更を指示するタスク」ではなく「結果を受け持つ責任」を渡すよう求める
  • 完了の判定を作業するエージェント自身に任せない。Missions は合意済みの基準で結果を確かめる独立した AI judge を置き、Devin Bots は CI と Devin Review を通った PR だけをマージする。Genie ZeroOps は修正案をユニットテストとサンドボックスでの dry run で確かめてから PR にする
  • 人への確認は、毎ステップの承認ではなく「判断が要る箇所」に集める。Devin Bots は人の判断が必要な案件を Needs You の受信箱に回す。Microsoft Autopilot は送信・共有・削除・変更の前に別の AI モデルが依頼内容と照合し、合致しない行為だけを人の承認に回す。支払いは常に人の承認が要る
📐 パターン 1: 依頼の単位を「目標・成功条件・予算・境界」の取り決めにする

これまでのコーディングエージェントでは、人が仕事を分解し、「この画面を Android に移植する」のようなタスクを一つずつ渡してきた。Missions と Devin Bots は、分解そのものをエージェントに渡す。そのかわり、開始前に取り決めを作る。Replit Missions は目標を受け取ると、成功の定義を詰める質問を返す。営業の例では「何をエンタープライズ顧客と数えるか」「有償 PoC を目標の件数に含めるか」を確かめる。そのうえで上限金額（記事の例では 1,000 ドル）と、年契約の割引を出してよいかといった許容範囲を合意する。予算を使い切った時点で、目標が未達でも作業は止まる。Devin Bots では、エンジニアがスコープの成功条件、守るべき CI チェック、計算資源への追加支出を認めるかどうか、Bot が触れてよいシステムと変更してよい範囲を決める。

こうした取り決めが必要になったのは、作業時間が延びるほど最初の依頼の曖昧さが大きく響くからだ。数分で終わるタスクなら、結果を見て言い直せば済む。数日走るエージェントが「完了」の定義を取り違えると、その間の作業と費用がまるごと無駄になる。Cognition の記事は、Android の移植例で「機能を Android に移植する」と「Android を iOS と同等に保つ」を対比し、前者をタスク、後者を責任と呼んでいる。責任の形で渡すと、終わりのない継続業務も同じ枠組みで扱える。予算を取り決めに含めるのも同じ理由による。Fortune の取材で Cognition は、Bot ごとに予算を持たせ、出した成果と突き合わせると説明した。並列に走るエージェントの数は費用にそのまま効くので、上限がなければ止める根拠もない。

Replit Missions
開始時の質問で成功の定義を詰め、上限金額・許容するトレードオフ・承認ゲートを「Missions agreement」として合意する。予算が先に尽きたら目標未達のまま停止する
11 月 17 日の公式ブログは、見込み客への連絡、提案書の共有、顧客向け資料の変更、製品仕様の約束を承認ゲートの例に挙げ、進め方が変わってもこの制限は維持されると書いている。社内で作った監視基盤 DataCat は、3,000 ドルの上限内で 2 日で構築したという。数値は Replit 自身の検証で、元のサービスや本番環境での性能を示すものではないと記事中で断っている。

Cognition Devin Bots
Bot には「バックログではなく目標」を渡す。Bot は調査し、作業ごとに Devin セッションを立てて委任し、結果を評価して次に何をやるかを決める。成功条件・守るべき CI・支出とリリースの承認要否は人が設定する
Android Bot は 44 日間で 1,134 件の PR をマージし、1,217 件のチケットを閉じた。その間に担当エンジニアが送ったメッセージは 183 件で、44 日のうち 22 日は 1 件も送っていない（いずれも Cognition の発表値）。目標を渡す方式で、人の関与がどこまで減るかを具体的な数字で示した事例だ。
📄 一次ソース
示唆: 長時間エージェントを導入するなら、最初に書くのはプロンプトではなく取り決めだ。成功条件、上限金額、変更してよい範囲、承認が要る行為の 4 項目を埋められない仕事は、まだ目標として渡せる段階にない。人がタスクに分解して渡すほうが安全だ。
📐 パターン 2: 完了の判定を作業者の外に置く

二つ目の共通点は、作業したエージェントに「終わった」と言わせないことだ。Replit Missions では、合意した成功基準に照らして結果を確かめる独立した AI judge が別にいる。作業側のエージェントは judge のフィードバックを受けて作業をやり直し、基準を満たしたときだけ Mission が完了になる。Devin Bots は、人が書いたコードと同じ CI と、コードレビュー用の Devin Review を通った PR だけをマージする。画面録画や変更前後の動画も添える。Layout Bot はチェックが落ちると、まず再実行してタイミング由来の揺らぎではないことを確かめ、それから原因の PR を突き止める。Databricks Genie ZeroOps は、修正案をユニットテストとサンドボックスでの dry run で検証してから、新しいブランチに PR として出す。

判定を外に出すのは、長く走るエージェントほど自分の作業を甘く評価する機会が増えるからだ。数日分の作業を一つのエージェントが自己申告で完了させると、人はその申告と成果物の両方を一から確かめ直すことになる。基準を事前に合意し、別の評価者かテストに判定させれば、人が見るのは判定が通ったものだけで済む。ただし判定役が機械である以上、評価者自身の誤りは残る。Microsoft も Autopilot の文書で、承認や進捗のメッセージを完了の証拠と見なさず、出力先で実際の結果を確かめるよう求めている。Cognition の記事も、テスト、ベンチマーク、ユーザーフローの実行、本番の挙動といったフィードバックの仕組みはエンジニアが用意するものだと位置付けている。

Databricks Genie ZeroOps（公開ベータ）
ジョブ・パイプライン・テーブルの障害を検知して原因を調べ、修正案をユニットテストとサンドボックスでの dry run で確かめてから、新しいブランチに PR として出す。本番のコードとデータは人のレビューなしに変更しない
11 月 19 日の公式ブログによると、非公開プレビューでは数百社・8 万件超のパイプライン障害を観測し、その半分以上は修正に企業固有の知識が必要だった。これを受けて、既知の不安定なデータソースや好みの修正方針を書けるカスタム指示を加えた。検証の場をサンドボックスに置き、出力を PR に限っているので、判定と適用が別々の段階に分かれている。
📄 一次ソース
示唆: エージェントに目標を渡す前に、完了を判定するテストか評価基準を用意する。用意できない仕事は判定を人が抱えることになり、長時間走らせても人の確認作業が減らない。
📐 パターン 3: 人の確認は「判断が要る箇所」に集める

三つ目は、人への確認の出し方だ。毎ステップ承認を求めると、数日走るエージェントの利点が消える。各社は、人に回す案件を選別して一か所に集める。Devin Bots は人の判断が必要な案件を Needs You の受信箱に回し、日次レポートと録画を Slack に流す。約 20 の Bot と 1 人の人間で運営するゲームスタジオの例では、取りまとめ役の Bot が 1 日 4 回、判断事項を一つの Slack スレッドにまとめる。Microsoft Autopilot は、読む・検索する・下書きする操作は止めずに実行し、一部を抜き取りで確認する。送信・共有・削除・変更と、自動化の作成・変更については、別の AI モデルが実行前に依頼内容と照合し、合致すれば実行し、合致しなければ Teams の承認カードで人に確認する。支払いと機微なブラウザ操作は常に人の承認が要る。Replit Missions は、受け取る通知の種類（ブロッカー・進捗・状況）と頻度（即時・日次・週次）を利用者が選ぶ。

確認の基準は行為の種類で切るのが共通している。どこまで任せるかは事前の取り決めで決まっているので、実行時に人へ回るのは、取り決めの範囲外か、取り返しのつかない行為だけになる。Autopilot は、承認の根拠になるのは所有者本人の依頼だけで、メールや文書、Web ページの中の指示は承認にならないと明記している。照合役のモデルは、外部の文章に紛れ込んだ指示による行為も止める位置にある。一方で、この照合の仕組みは今回のリリースでは管理者も利用者も設定を変えられない。Fortune の取材で Cognition は、低リスクの変更はチームが自動承認にできると説明しており、閾値をどこまで利用者に開くかは各社で分かれている。

Microsoft Autopilot（Frontier プレビュー）
送信・共有・削除・変更と自動化の作成・変更は、第二の AI モデルが依頼内容と照合し、合致すれば実行、しなければ承認待ちにする。支払いと機微なブラウザ操作は常に承認が要る
管理者向け文書は、Autopilot が依頼を意図より広く解釈しうると書き、「古いプロジェクトファイルの整理」が想定より多くの内容に及ぶ例を挙げている。既定では無効で、Frontier 登録・支出ポリシー・エージェントの有効化の 3 つがそろわないと使えない。支出ポリシーの上限に達すると、自動化と監視の処理を止め、新しい依頼にも応じなくなる。このとき利用者には理由が表示されない、と注意書きがある。
📄 一次ソース
示唆: 承認ポリシーは「読む・下書き」「依頼と照合して自動実行」「常に人が承認」の 3 段で設計する。境界は行為の種類で決め、外部の文章に含まれる指示を承認の根拠にしない。予算切れで止まったことを利用者に通知する経路も、別に用意しておく。
✍️ 編集後記 エージェントの作業時間が延びると、人の仕事はタスクの指示から、契約の締結と検収に近づく。今週の各社の発表は、エージェントの能力よりも、成功条件・予算・承認境界という取り決めの書式をそろえることに力を割いていた。どの製品を選ぶかより先に、自分たちの仕事で「合格」を機械が判定できる形に書けるかを確かめておきたい。
