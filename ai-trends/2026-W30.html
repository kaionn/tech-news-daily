コンテキストエンジニアリングの実装論 — 「何を読ませるか」がプロンプト文面より重要になった

「プロンプトエンジニアリング」から「コンテキストエンジニアリング」へ、という言葉の置き換えが急速に広まった。背景にあるのは、エージェントが長時間・多ステップのタスクをこなすようになったことで、モデルに何を読ませるかの設計がプロンプト文面の工夫よりもエージェントの性能とコストを左右するようになったという実務側の実感だ。Anthropic・Cursor・Manus という立場の異なる3社が、期せずして同じ結論——『全部を先に詰め込まず、必要な分だけ実行時に取りに行き、キャッシュを壊さない』——にたどり着いている。

TL;DR — 3 行で
  • エージェント設計の焦点はプロンプト文面から、コンテキストに何を・いつ入れて何を捨てるかという『コンテキストエンジニアリング』に移った
  • Claude Code や Cursor は全部を先読みせず、ファイルパスなど軽量な参照を持たせて実行時にオンデマンド取得する設計に収束している
  • Manus の実運用データでは KV-cache のヒット率がコストを10倍左右しており、コンテキスト設計は性能だけでなくコストの問題でもある
📐 パターン 1: 全部詰め込む設計から、実行時に取得する設計へ

コンテキストエンジニアリングの共通パターンは「事前にすべてを詰め込まない」ことだ。エージェントにはファイルパスや保存済みクエリのような軽量な参照だけを持たせ、必要になった瞬間に head や tail のようなコマンドでデータを実行時に読み込む。これが Just-In-Time 方式と呼ばれる設計で、静的に全データを先読みする方式と対比される。

この方式が主流になったのは、コンテキストウィンドウが大きくなってもモデルの実効性能は単調に上がらないためだ。無関係な情報が混じるほど注意が散り、矛盾した情報が入り込むリスクも増える。先読みで「念のため全部入れる」設計はコストとノイズの両方を増やすだけで、実行時に必要な分だけ取りに行く方が結果的に安定する。

Claude Code（Anthropic 公式エンジニアリングブログ）
ファイルパス・保存済みクエリ・URL などの軽量な参照だけをコンテキストに持たせ、head/tail 等のコマンドで実行時にオンデマンド読み込みする
Anthropic のエンジニアリングブログが Just-In-Time retrieval の具体例として、大きなデータセットを全読みせず head/tail で扱う手法を挙げている

Cursor（公式ブログ「Dynamic context discovery」）
静的に情報を詰め込む設計から、エージェントが必要な情報だけを実行時に発見して取りに行く『動的コンテキスト発見』へ移行
2026年1月6日公開の記事で、ツール出力をファイルに書き出し tail で追う手法や、MCP ツールの説明を選択的にロードして総トークン数を46.9%削減した実測値を報告している

示唆: エージェントを設計するときは、まず『何が必要か』ではなく『いつ取得すればよいか』を先に決める。全部を先読みする設計は後から効率化しづらいので、最初から参照ベースの実行時取得を前提に組んだほうがよい。
📐 パターン 2: 長時間タスクの記憶: 圧縮とメモとサブエージェントへの分割

タスクが長時間・多ステップに及ぶと、会話履歴そのものがコンテキスト上限を圧迫する。Anthropic が挙げる対策は大きく3つで、上限に近づいたら履歴を要約して圧縮する compaction、NOTES.md や To-Do リストのようにコンテキスト外に進捗を書き出す構造化メモ、検索など詳細なやり取りをサブエージェントに閉じ込めて要約だけを親エージェントに返す分業、である。

この3つが同時に語られるのは、単純な要約だけでは「何を消して何を残すか」の判断がモデル任せになり事故が起きやすいからだ。アーキテクチャ上の決定や未解決のバグは残しつつ冗長なツール出力は捨てる、という粒度の使い分けが必要で、外部ファイルへの書き出しとサブエージェントへの分離はこの判断を設計時に固定しておくための仕組みといえる。

Claude Code（Anthropic 公式エンジニアリングブログ）
コンテキスト上限が近づくと会話履歴を要約し直す compaction と、To-Do リスト形式の構造化メモを併用する
compaction では『アーキテクチャ上の決定や未解決のバグは保持し、冗長なツール出力は破棄する』という基準が明示されている
📄 一次ソース
Cursor（公式ブログ「Dynamic context discovery」）
圧縮でロスした情報を、チャット履歴をファイル化して検索し直すことで復元できるようにする
コンテキスト上限到達後もエージェントが履歴ファイルへの参照を持ち、必要になれば検索して重要な詳細を取り戻せる設計
📄 一次ソース
示唆: 圧縮ロジックだけに頼ると情報欠落が起きるので、圧縮後も参照可能な外部メモ（ファイルやサブエージェントの出力）を必ず残す設計にする。
📐 パターン 3: コンテキスト設計はコストとレイテンシの問題でもある

Manus は本番運用の実測として、KV-cache のヒット率を「本番エージェントで最も重要な単一指標」と位置づけている。Claude Sonnet の場合、キャッシュされた入力トークンは 0.30 USD/MTok、キャッシュされないトークンは 3 USD/MTok と10倍のコスト差があり、プロンプトの先頭を毎回変えるだけでキャッシュが丸ごと無効化される。

この制約は設計そのものに跳ね返る。Manus はツールを動的に増減させるとキャッシュが壊れるため、ツール自体は消さずにロジットマスキングで選択肢を制限する状態機械を採用した。Cursor が MCP ツールの説明を選択的にロードして総トークン数を46.9%削減したのも同じ問題意識で、コンテキスト設計は「モデルに何を見せるか」だけでなく「キャッシュとコストにどう影響するか」まで含めて評価する必要がある。

Manus（公式ブログ）
プロンプト先頭を固定しツールを動的に消さないことで KV-cache のヒット率を維持し、ツール制御はロジットマスキングの状態機械で行う
Claude Sonnet でキャッシュ有無により入力トークン単価が10倍（0.30 USD/MTok 対 3 USD/MTok）異なると具体的な数値で報告している
📄 一次ソース
Cursor（公式ブログ「Dynamic context discovery」）
MCP ツールの説明をフォルダ単位で同期し選択的にロードすることで総エージェントトークン数を46.9%削減
全ツールを常時ロードするのではなく必要な分だけ読み込む設計変更の効果を実測値として公開している
📄 一次ソース
示唆: コンテキスト設計をレビューするときは機能面だけでなく、プロンプト先頭の安定性やツール定義の変更頻度がキャッシュ効率をどれだけ壊しているかも点検項目に加える。
✍️ 編集後記 3社の記事に共通するのは、コンテキストエンジニアリングが結局『プロンプトの文面をどう書くか』ではなく『何を・いつ読み込み、いつ捨てるか』というシステム設計の話に収斂している点だ。プロンプトエンジニアリングの次の主戦場はここに移った。
