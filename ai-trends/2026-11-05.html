今号のテーマ AGENTIC-TESTING

E2E テストのエージェント化は「毎回モデルに操作させる」をやめ始めた — 操作は記録して再生、判定は別系統で確かめる、CI には決定論的なテストを残す

10月29日、InfoQ は Linearbytes の Bug0 QA Agent を取り上げた。自然言語で書いたテスト手順をエージェントが実行し、成功した操作を具体的なブラウザ操作として保存して、次回からはモデルを呼ばずに再生する。同じ発想は、GitHub で 1.3 万スターを集める OSS の e2e にもある。「目標を伝えればエージェントがアプリを操作する」型のテストは 1 年ほど前から各社が出してきた。ただし Slack Engineering が 6 月に公開した社内検証では、エージェント実行は 1 回 15〜30 ドル、10 分を超えることもあった。毎回のプルリクエストで回せる値段ではない。いま各社の設計は、エージェントに何をさせ、何をさせないかの線引きに移っている。操作をキャッシュする、判定を操作役とは別のモデルやエージェントに任せる、CI には生成済みの決定論的なテストを残す、の三つだ。

TL;DR — 3 行で
  • e2e と Bug0 QA Agent は、エージェントが一度成功させた操作を記録し、次回以降はモデルを呼ばずに再生する。UI が変わって再生が失敗したときだけエージェントを呼び直す
  • 判定は操作役から切り離されている。Bug0 はアサーションをキャッシュせず、毎回 Claude と Gemini に別々に評価させて、割れたら 3 つ目のモデルが決める。Momentic の Mo では、別のエージェントが新しいセッションで再現できた不具合だけを確定扱いにする
  • Slack の検証では、エージェント実行は 1 回 15〜30 ドルかかった。生成済みの Playwright テストなら実行は 30〜45 秒で済む。同社は、CI の土台を決定論的テストに置き、エージェントは探索とデバッグに使う組み合わせを推している
📐 パターン 1: 操作は一度だけ推論し、あとは再生する

OSS の e2e では、テストは TypeScript で書く。agent.act() に自然言語の目標を渡すとエージェントがアプリを操作し、結果は agent.assert() による自然言語の確認と、expect(screen.getByRole('status')) のような通常のロケーターのアサーションを同じテストの中で混ぜて検証できる。README によれば、後続のアサーションで検証されたエージェントステップは操作を記録し、次回の実行では「アプリが変わるまでモデル呼び出しなしで」それを再生する。Bug0 QA Agent も構造は近い。単一操作のステップが成功すると、その操作を具体的なブラウザ操作にコンパイルしてインメモリの Redis に保存し、次回からは Playwright で直接再生する。再生が UI の変更で失敗した場合は、テスト全体を失敗にせずキャッシュを無効化して、マルチモーダルのエージェントループを呼び直す。

こう設計する理由はコストと速度だ。Slack の検証では、エージェント実行のトークン消費は 1 フローで 350 万〜600 万に達した。その大半はモデルの出力ではない。毎ターン送り直されるシステムプロンプトと会話履歴、特にブラウザのアクセシビリティスナップショットが占めていた。毎回推論していると、この再送コストがテストのたびに積み上がる。記録と再生に分ければ、モデルを呼ぶのは「初回」と「UI が変わったとき」だけになる。ただし限界もある。Bug0 のキャッシュは単一操作のステップにしか効かず、複数の操作を含む指示は毎回エージェントが実行し直す。e2e も、アプリの変更をどう検知してキャッシュを捨てるかを README では説明していない。キャッシュがどの単位で、いつ無効になるかが、この方式のコストを決める部分として残っている。

e2e（tester-army/e2e、Apache-2.0）
検証済みのエージェントステップの操作を記録し、アプリが変わるまでモデル呼び出しなしで再生する
1 つのテストファイルに自然言語の目標とロケーターのアサーションを同居させ、エージェントを使わないテストはモデル自体を必要としない。変更に影響しないテストを除外する @e2e-dev/decision や、Claude Code / Codex 上でエージェントステップを動かす @e2e-dev/acp を別パッケージで提供している。1.0 に向けて開発中で、API はマイナーリリース間でも変わり得ると明記している

Bug0 QA Agent（Linearbytes、FSL-1.1-ALv2）
成功した単一操作をブラウザ操作として Redis に保存して再生し、再生が壊れたらキャッシュを捨ててエージェントを呼び直す
記録と再生を CI 向けの既定動作にした例。InfoQ は、キャッシュが単一操作のステップに限られ、複数操作の指示は毎回エージェント経由で実行される点を注意点として挙げている。ライセンスは最初の 2 年間に競合利用の制限が付くソースアベイラブルで、オープンソースではない
📄 一次ソース
示唆: エージェント型テストを CI に入れるなら、まず「どの操作をキャッシュでき、何が起きたらキャッシュを捨てるか」を確かめる。毎回推論する前提の見積もりのままでは、テスト本数が増えた時点で費用が合わなくなる。
📐 パターン 2: 操作役に合否を判定させない

操作をキャッシュしても、判定まではキャッシュしない製品が多い。Bug0 はアサーションを毎回ビジョンモデルで評価し、Claude と Gemini がそれぞれ独立に判定して、意見が割れたら 3 つ目のモデルが決める。Momentic の Mo はエージェントの役割で分けている。セッションエージェントが計画を立てて重複を除き、探索エージェントは製品の一部を見て回って「疑わしい不具合」を報告するが、確定はしない。機能的な不具合の疑いは、バグ再現エージェントが別のブラウザやデバイスのセッションで最初からフローをたどり直す。再現できなければ、確定した不具合としては報告されない。誤字のような静的な指摘は、この再現を省いてスクリーンショットを証拠にする。

判定を切り離すのは、操作したエージェント自身の「おかしい」という判断が信用できないからだ。InfoQ の記事は、最良の自律テストエージェントでも人間のテスト担当者と判断が一致したのはテスト実行の約 60% だったという Chevrot らの研究を引いている。不一致の原因は、モデルの見間違いのこともあれば本物のバグのこともあり、外からは区別がつかない。研究の側でも、2026 年 2 月に公開された WebTestPilot が、合否の基準（オラクル）を自然言語の仕様から推論する難しさを中心課題に据えている。製品側の答えは、別のモデルや新しいセッションで同じ結論が出るかを確かめることだ。これは本誌 10 月 17 日号で扱った AI コードレビューの「発見と検証の分離」と同じ構造になっている。

Momentic Mo（bug bash）
探索エージェントは疑いの報告までにとどめ、バグ再現エージェントが新しいセッションで再現できたものだけを機能的な不具合として確定する
報告にはそれぞれ期待した動作・実際の動作・再現手順が付く。役割ごとにエージェントを分け、「見つける」と「確かめる」を同じエージェントにさせない構成を製品のドキュメントで明示している
📄 一次ソース
示唆: エージェントの「失敗」や「バグ発見」の報告をそのまま信じない。別のモデルか別のセッションで再確認する工程を最初から入れておけば、誤検知を人が仕分ける手間が減る。
📐 パターン 3: CI の土台は決定論的テストに残す

Slack は Thread Reply（15〜20 ステップ）と Search Discovery（25〜30 ステップ）の 2 フローで、3 つの方式をそれぞれ 20 回ずつ実行した。Playwright MCP 経由のエージェントは失敗率 0%〜約 12% で、実行は約 5〜8 分。Playwright CLI 経由は約 12〜20% で、約 9〜11 分。エージェントに Playwright のテストコードを生成させる方式は、複雑な方のフローで失敗率が約 48% まで上がった。一方、生成済みテストの実行そのものは 32〜45 秒だった。エージェントが同じ操作順序をたどった実行は約 20% にとどまり、ゴールには届くものの経路は毎回違った。Playwright 本体も、テスト計画を Markdown で specs/ に書く planner、計画を実行してセレクターとアサーションをその場で確かめながら tests/ にテストを書く generator、失敗したテストを直す healer の 3 つのエージェントを用意している。いずれもエージェントの出力を、リポジトリに残る普通のテストコードにする設計だ。

各社がこの分担に落ち着きつつあるのは、エージェントの強みと CI の要件が合わないからだ。エージェントは UI が少し変わっても目標にたどり着けるが、経路が毎回変わるので、失敗を前回と比べにくい。CI に必要なのは、同じ入力で同じ結果が出ることと、失敗をすぐ切り分けられることだ。Slack は、決定論的テストを CI の安定した土台にし、エージェントは探索・デバッグ・複雑な振る舞いの検証に使う組み合わせを結論にした。Momentic も、Mo はテストファイルを書かないとしたうえで、繰り返し実行するチェックはリポジトリの Momentic テストとして CI で回すよう案内している。healer が「機能が壊れている」と判断したときにテストを直さずスキップする点も同じ考え方から来ている。テストを通すことより、壊れた事実を残すことを優先している。

Slack Engineering（エージェント型 E2E テストの社内検証）
200 回超の実行で、エージェント実行・CLI 実行・テストコード生成の失敗率、実行時間、トークン消費を比べた
エージェント実行は 1 回 15〜30 ドルで、10 分を超えることもあった。コストの主因はモデルの出力ではなく毎ターンの文脈の再送だと分析している。頻繁な CI 実行よりも、的を絞ったデバッグや探索的テストに向くと結論づけた

Playwright Test Agents（planner / generator / healer）
エージェントの出力を Markdown の計画と通常の Playwright テストにし、修復も既存テストへのパッチとして扱う
healer は失敗した手順を再実行し、現在の UI から同等の要素を探して、ロケーターの更新や待機の調整などのパッチを提案する。テストが通るかガードレールが止めるまで繰り返し、機能が壊れていると判断した場合はテストをスキップする
📄 一次ソース
示唆: エージェントには「テストを書く・直す・探す」を任せ、CI で毎回走らせるのは生成済みの決定論的テストにする。エージェントの実行結果を CI の合否にそのまま使うのは、コストと再現性の両面でまだ早い。
✍️ 編集後記 エージェント型テストの各社の工夫は、どれもエージェントを「呼ばない」方向に向いている。操作は一度だけ推論して再生し、判定は別の目で確かめ、毎回の CI は生成済みのコードに任せる。エージェントを使うのは、結果を固定した成果物に変えられる場面に絞られつつある。
