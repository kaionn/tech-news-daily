今号のテーマ AGENT-IDENTITY

エージェントの身元は「ユーザーの借り物」から「専用の ID」へ — 代理と自律の区別、ID を切る単位、受け手側での識別

社内システムを操作するエージェントは、これまで大半が「呼び出したユーザーのトークン」か「アプリ共通のサービスアカウント」で動いてきた。どちらでも動くことは動く。ただ監査ログには人間かアプリの名前しか残らず、ある一つのエージェントだけを止める手段もない。10月8日、Google は Gemini at Work 2026 で Gemini agent を発表し、常駐する coworker agent に専用の ID と @agents.company.com のメールアドレスを持たせると明記した。Microsoft Entra Agent ID はすでに agent identity・blueprint・agent's user account という 3 種類のディレクトリオブジェクトを定義しており、Okta は 8月に Agent SSO を GA にして、エージェントを社員と同じディレクトリに登録する形にした。受け手の側でも、Sierra が 10月8日に電話の相手が AI かどうかを判定する fleming-1 を出している。エージェントを「誰か」として扱うための設計が、発行側と受け手側の両方で具体的になってきた。

TL;DR — 3 行で
  • Entra Agent ID はトークンの subject と actor を分ける。自律動作のときは subject がエージェント自身になり、ユーザーの代理のときは subject がユーザー、actor がエージェントになる。Google の coworker agent も「あなたではなく自分の ID で動き、共有されたものしか見ない」と定義され、操作は人ではなくエージェント名義で監査ログに残る。
  • ID をどの単位で作るかについて、Microsoft はエージェントの種類（blueprint）と信頼境界で切るよう指示し、スケールアウトのレプリカ・セッションごと・会議や文書ごとに ID を作るのは避けるべきパターンとしている。Okta Agent SSO は認可を各アプリから IdP に移し、保存したクレデンシャルの代わりに有効期限の短いトークンを発行する。
  • 名乗らずにかけてくるエージェントは、受け手が見分けるしかない。Sierra の fleming-1 は通話音声を通話中にリアルタイムで採点し、Decagon も名乗らない個人エージェントの検出を Personal Agent Gateway に入れた。どちらも検出結果を「判断材料」として渡すだけで、遮断するかどうかは企業のポリシーに任せている。
📐 パターン 1: 「誰として動くか」をトークンの subject と actor で分ける

Microsoft Entra の agent identity は特殊なサービスプリンシパルで、自分ではクレデンシャルを持たない。トークンは、テンプレートにあたる agent identity blueprint が federated identity credential などを使って代わりに取得する。取得の仕方は 2 通りある。自律エージェントはアプリトークンを取り、その subject はエージェント自身になる。ユーザーに呼び出された対話型エージェントはユーザートークンを取り、subject はユーザー、actor はエージェントになる。さらに Exchange や Teams のようにユーザーオブジェクトが必須のシステム向けには、agent identity と必ず 1 対 1 で対応する agent's user account を別に発行できる。Google が 10月8日に発表した Gemini agent も同じ線引きをしている。一つのタスクのためにその場で作るサブエージェントとは別に、役割を持って常駐する coworker agent には専用の ID とメールアドレスを与え、全操作をエージェント名義で監査ログに書く。

ユーザーのトークンをそのまま使い回す方式から各社が離れた理由は、監査と停止の単位にある。ユーザーのトークンで動いたエージェントの操作は、ログ上ではその人自身の操作と見分けがつかない。エージェントだけを止めるには、その人のセッションごと失効させるしかない。subject と actor を分ければ「誰の権限で」と「誰が実行したか」を別々に記録できる。自律エージェントに専用の ID を持たせれば、そのエージェントだけを無効化できる。Entra の agent identity に「sponsor」という欄があり、インシデント時に連絡する責任者の人間を記録するのも、エージェントの責任を最終的に人へ結びつけるための設計だ。

Microsoft Entra Agent ID（agent identity / agent's user account）
自律動作では subject をエージェント自身に、代理動作では subject をユーザー・actor をエージェントにする。クレデンシャルは blueprint 側だけが持つ
代理と自律の区別をトークンのレベルで定義している。ユーザーオブジェクトが必須の M365 系システムのために、agent identity と 1 対 1 で固定された user account を別に用意する点まで公式ドキュメントに明記されている。

📄 一次ソース

📐 パターン 2: ID はエージェントの種類と信頼境界の単位で作り、認可は IdP に寄せる

エージェント専用の ID を導入すると、次に「いくつ作るか」が問題になる。Microsoft の Entra Agent ID 設計パターン集は、ID を切る単位を 2 つに絞っている。1 つはエージェントの種類で、同じ blueprint から作った ID には条件付きアクセスや無効化を一括でかけられる。もう 1 つは信頼境界で、別のランタイム・シークレット・チームにまたがるワーカーには別の blueprint を割り当て、1 か所の侵害がほかに波及しないようにする。逆に、スケールアウトのレプリカ、メモリのセッション分離、会議や文書ごとの ID 作成は、監査上の利点がないのに管理コストだけ増えるパターンとして避けるよう明記している。タスクの間だけ使う一時的な ID は認めているが、実行時に作るため遅延が読めない点を注意書きしている。

Okta は同じ問題を、認可をどこに置くかという面から整理した。8月24日に GA になった Agent SSO では、Cross App Access に対応したエージェントが社内アプリに接続した時点で、Okta がそのエージェントを社員と同じ Universal Directory に登録する。保存済みのクレデンシャルの代わりに、有効期限の短いトークンを発行する。基盤の Cross App Access は IETF で策定中の ID-JAG（Identity Assertion JWT Authorization Grant）で、IdP が発行した JWT を接続先の認可サーバーが自分のポリシーで評価してアクセストークンに引き換える。各アプリに個別に OAuth の同意を積み重ねる代わりに、人間の SSO と同じ場所でエージェントの権限を管理する。ID を細かく分けすぎない Microsoft と、IdP に一元化する Okta は、管理の単位をアプリやセッションではなく組織のディレクトリに置くという点で同じ方向を向いている。

Microsoft Entra Agent ID 設計パターン
ID は blueprint（エージェントの種類）と信頼境界で切る。レプリカ・セッション・オブジェクトごとの ID は避けるべきパターンとして明示
単体エージェント、逐次型マルチエージェント、オーケストレーター型、ユーザーごと、デジタルワーカーの 5 構成について、blueprint と ID の対応を具体的に示している。「何に ID を作らないか」まで書いた公式ガイドは珍しい。

📐 パターン 3: 名乗らないエージェントは、受け手が見分ける

発行側で ID を整えても、外から来るエージェントがすべて名乗るとは限らない。Sierra が 10月8日に出した fleming-1 は、電話の相手の音声をリアルタイムで解析し、AI が生成した音声の兆候を採点するモデルだ。人間の耳に自然に聞こえるかどうかではない手がかりを見るとし、ノイズの多い音声にも対応する。本物の人間を誤って AI と判定しないよう、既定では保守的な閾値に調整されている。Decagon も 10月1日の Personal Agent Gateway に、既存のチャネルで名乗らない個人エージェントを検出する機能と、エージェント専用の窓口を入れた。

両社に共通するのは、検出を「遮断」ではなく「判断材料」として扱っている点だ。Sierra は、検出結果をどう扱うかは企業が決めることだとし、銀行なら追加の本人確認を挟む、問い合わせの多い企業ならまずエージェントからの電話の割合を測るといった使い方を例に挙げている。消費者の代理エージェントからの問い合わせは正当な顧客の用件でもあるため、一律に拒否すれば顧客を失う。理想は相手が自分から名乗ることで、Sierra と Meta は 10月9日に Personal Agent Protocol の草案（Poppy）を公開し、セッションの冒頭でエージェントが必ず名乗る形を定めた。ただ全員がこれに従うまでの間は、名乗った相手を ID で認可し、名乗らない相手は推定で扱う二段構えになる。

Sierra fleming-1

対処を決めるのは企業側だと明言し、検出と処置を分けている。Sierra 上の音声エージェントであれば有効化するだけで使える。精度の数値は公表されていない。
