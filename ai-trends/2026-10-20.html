今号のテーマ AGENT-SCALE-INFRA

コーディングエージェントの書き込み量に、ソース管理と開発用 DB が作り替えられ始めた — 保存と配信の分離、ref 更新だけの協調、マージしない分岐

コーディングエージェントはほぼ一手ごとに commit・push し、その push ごとに CI が clone を走らせる。人間の開発速度を前提にしたインフラは、この書き込み頻度を想定していない。10月6日、GitHub は Git 基盤の作り直しを公表した。2026年9月の commit 数は 73.8 億件で前年の 5 倍超、push は月 33.5 億件で 4.9 倍だ。10月13日には Anthropic が、社内モノレポのマージが 5月の 1 日約 2,500 件から 9月には 3 万件超に増え、Git をやめて自社製のバージョン管理システム Scion に移行したと公開した。10月8日には Databricks が、並列に動くエージェントごとに Postgres を分岐させる開発フローを紹介している。3 社の対応には共通点がある。データを永続的に保存する層と配信する層を分けること、全体で調整が必要な箇所を ref の更新 1 か所に絞ること、そして分岐はマージしない前提で安く大量に作ることだ。

TL;DR — 3 行で
  • 保存と配信を分けた。GitHub は 5 台のファイルサーバーに全量を複製する構成をやめ、正本を Azure Blob Storage に置いてキャッシュ付きのワーカーで配信する構成に移る。Anthropic の Scion はサーバー側にも完全な作業コピーを持たず、3 段のキャッシュでヒット率 99% 超、CI のチェックアウトを約 100 倍速くした。
  • 全体で協調するのは ref の更新だけにした。GitHub はオブジェクトの保存・接続性の検証・シークレットスキャンを並列化し、社内ベンチマークで書き込みスループットが最大 35 倍になった。Anthropic は ref の更新を Spanner の 1 行に対する compare-and-swap にし、従来型のマージキューはやめて、マージ後とデプロイ前の自動テストで品質を守る。
  • 分岐はデータの側で大量に作り、マージしない。Databricks は git worktree の post-checkout フックで、エージェントごとに 1 秒未満で DB ブランチを作り、スキーマ変更だけをマイグレーションとして本番に反映する。ただし Columbia 大学のベンチマークでは、分岐を数千単位で作る用途に今の分岐可能 DB はまだ追いついていない。
📐 パターン 1: 永続化する層と配信する層を分ける

従来のソース管理は、データを失わないための複製と、読み出しをさばくための複製に同じコピーを使っていた。GitHub の現行構成 Spokes では、各リポジトリの全量を複数台（既定で 5 台）のファイルサーバーに持ち、quorum を使う 3 フェーズコミットで書き込む。読み出し能力を上げるためにレプリカを足すと、書き込みのたびに更新すべき永続コピーも増え、push の速さは一番遅いレプリカで決まる。新しい構成では、正本を Azure Blob Storage に置き、読み出しはリポジトリのデータをキャッシュする軽量ワーカーが担う。ワーカーが落ちても、失うのはキャッシュだけになる。Anthropic の Scion はさらに進んで、クライアントを常時オンラインの薄い存在として扱う。履歴・blame・コミット・マージ・リベースはサーバーが持つ。各ノードの scion-daemon、リージョンの scion-cache、正本を Spanner やクラウドストレージから読む scion-server の 3 段構成で、クライアントは必要なツリーと blob だけを取りに行く。

この方向に進んだのは、エージェントと CI ジョブが常にオンラインで、手元に完全なコピーを必要としないからだ。Git はオフラインで作業するクライアントが全量を持つことを前提に設計されている。Anthropic の CI は 1 日約 2,500 万回チェックアウトしており、素直に fetch すれば 1 日 600 PB を超える転送量になる。shallow clone や sparse checkout で回避はできるが、そのぶん運用の負担が積み上がる。同社は数百台の Git ミラーを運用していたが、マージ量が増えるにつれて手に負えなくなった。GitHub も、読み出しはキャッシュとレプリカで比較的簡単に増やせるが、書き込みは永続化と一貫した可視化が終わるまで次に進めないため難しいと書いている。両社とも、読み出しの規模を永続化のコピー数から切り離すことで、この問題を解いた。

GitHub（Git 基盤の再構築）
全量を 5 台に複製して quorum で書く構成から、Azure Blob Storage を正本とし、キャッシュ付きの計算ワーカーで配信する構成へ
2025年9月から2026年8月で Git の月間イベント数は 2,182 億件から 4,733 億件に倍増し、最も混むリポジトリは 8月に約 10 億リクエストを受けた。新しい構成ではワーカーをトラフィックに合わせて増減でき、圧縮やガベージコレクションも配信ホストとは別のワーカーで実行する。

Anthropic Scion（社内バージョン管理システム）
履歴はサーバーが持ち、クライアントは容量に上限のあるキャッシュだけを持つ。daemon → リージョンキャッシュ → サーバーの 3 段で、ヒット率は 99% 超
main の履歴は約 100 GB、圧縮後の作業コピーは 25 GB を超える。移行後、旧 Git ミラー構成と比べて CPU とメモリの使用量は約 200 分の 1、チェックアウトは約 100 倍速くなり、CI だけで CPU 容量に約 25% の余裕ができた。7 人のチームが 5 か月で移行した。同社自身は、Git の汎用的な代替にはならないと明記している。
📄 一次ソース
示唆: エージェントが CI やリポジトリに与える負荷を見積もるときは、書き込み量だけでなく、1 回の push のあとに発生する clone・fetch の回数を数える。読み出しの増加に永続化のレプリカを足して対応している構成は、書き込みを遅くする。まずは CI 用のキャッシュ層を一段挟めるかを検討するとよい。
📐 パターン 2: 全体で調整する箇所を ref の更新 1 か所に絞る

2 つ目の共通点は、書き込みのうち排他制御が必要な部分を最小にしたことだ。GitHub の新しい書き込み経路では、調整が必要なのは ref の更新だけになる。オブジェクトの保存、接続性の検証、シークレットスキャンは、他の書き込みと並列に進められる。push の完了までに直列で待つ処理が短くなり、社内ベンチマークでは書き込みスループットが最大 35 倍になった。Anthropic の Scion では、ref の更新は Spanner の 1 行に対する compare-and-swap で、changeset の作成とは分けて処理する。さらに、main とリリースブランチ以外の ref（ブランチやタグ）を作ることを推奨していない。すべてのサーバーが合意しなければならないグローバル状態は、それ自体がスケールの障害になるからだ。

この考え方は、マージキューの扱いにも及ぶ。マージキューは、単独では通る 2 つの変更が main 上で組み合わさって壊れるのを防ぐため、変更を直列に検証する。Anthropic は、テストを回している間に数百の変更が入ってくる規模では従来型のマージキューは成り立たないと判断した。キュー全体にリポジトリ単位のロックをかける方式も再現できなかった。代わりに、マージ後とデプロイ前の自動テストに投資し、同時に入った変更の衝突は Claude が人間より早く解消する運用にしている。人間のレビューは全行を読むことをやめ、変更の意図を確認する形に変わった。新しいレビューツール Antique は、コメントだけの変更と重要なロジックの変更を区別して承認ルールを変える。品質を守る仕組みを、マージの前からマージの後へ移したといえる。ただし、これは衝突を高速に直せるエージェントが常にいることを前提にした判断だ。

GitHub（書き込み経路の縮小）
ref の更新だけを調整し、オブジェクトの保存・接続性検証・シークレットスキャンは並列に実行する
GitHub は、エージェント規模で問題になる圧力として、push 1 回の待ち時間、1 リポジトリへの書き込みの集中、単一 ref の取り合い、push 後の大量の読み出しを挙げている。そのうえで、ブランチ保護・必須レビュー・監査ログはそのまま残し、メンテナンスウィンドウなしで移行するとしている。

Anthropic（マージキューの廃止）
ref 更新は Spanner の 1 行への compare-and-swap、トランクベース開発、マージ前のキューの代わりにマージ後・デプロイ前の自動テスト
1 日 3 万件超のマージでは、テスト中に数百の変更が入るため、直列に検証するキューは追いつかない。検証をやめたのではなく、検証するタイミングを変えた事例だ。
📄 一次ソース
示唆: エージェントによる PR が増えてマージキューが詰まり始めたら、キューを速くする前に、どの不変条件をマージ前に守る必要があり、どれならマージ後のテストとロールバックに任せられるかを分けて考える。マージ後に任せる判断は、衝突を素早く直す手段とデプロイ前のテストがあって初めて成り立つ。
📐 パターン 3: 分岐はデータの側で大量に作り、マージしない

コードの側では分岐を減らす一方で、データの側では分岐を増やす動きが進んでいる。Databricks が 10月8日に紹介した Lakebase（Neon の技術を使った Postgres）のフローでは、git worktree で各エージェントに作業ディレクトリとブランチを与え、post-checkout フックで同じ名前の DB ブランチを自動で作る。PR を開くと、GitHub Actions が本番の子ブランチを作ってマイグレーションを流し、スキーマの差分を PR にコメントする。この DB ブランチは PR を閉じるかマージした時点で削除される。copy-on-write なので、DB のサイズに関係なく 1 秒未満で分岐でき、増えるストレージは差分の分だけだ。アイドル中のブランチは計算資源がゼロまで縮む。重要なのは、DB ブランチを親にマージしない点だ。本番に戻すのはコードとして管理したスキーマ変更（Drizzle、Flyway、Alembic などのマイグレーション）だけになる。

コードのブランチを減らす Anthropic と、DB のブランチを増やす Databricks は、逆のことをしているように見えるが、原則は同じだ。全体で合意が必要な状態を増やさないということだ。マージしない使い捨ての分岐は、作ってもグローバル状態を増やさないので安く量産できる。共有のステージング DB では、エージェント同士がスキーマ変更で衝突したり、モックで済ませたりしてしまうので、この分離は効果がある。ただし、分岐を大量に作る用途への対応はまだ途上だ。Columbia 大学 DAPLab の BranchBench では、Neon はブランチ内の読み出しや結合は速いものの、ブランチの作成が最大 25 倍、切り替えが最大 1,500 倍遅く、アクティブブランチ数の上限 20 にも達した。1,000 ステップの探索ワークロードでは、Neon は 33 ステップ、Dolt は 2 時間で 170 ステップしか進まなかった。

Databricks Lakebase（エージェント別 DB ブランチ）
worktree の post-checkout フックでエージェントごとに DB ブランチを作り、PR ごとに本番の子ブランチを作って閉じたら削除する。ブランチはマージせず、マイグレーションだけを反映する
共有 DB の取り合いを、copy-on-write の分岐で避ける構成をコード例付きで示している。本番から分岐させると個人情報が開発環境に出るため、シード済みの DB から分岐させる運用が一般的だとも書いている。
📄 一次ソース
BranchBench（Columbia 大学 DAPLab）
分岐・変更・評価・破棄を繰り返すエージェント型ワークロードで、Postgres の CoW クローン、Dolt、Neon などの分岐可能 DB を比較した
ブランチの管理を速くするとブランチ内の処理が遅くなり、その逆も起きるというトレードオフがあることを示し、安い分岐を数千個作れる DB はまだないと結論づけた。PR 単位の分岐は今でも実用になるが、探索のために大量に分岐させる用途は時期尚早だと判断する材料になる。
📄 一次ソース
示唆: 並列エージェントに開発用 DB を与えるなら、共有のステージング DB ではなく PR やエージェント単位の使い捨てブランチにし、本番に戻すのはマイグレーションだけにする。1 タスクで数十〜数千の分岐を作る設計は、使う DB の上限ブランチ数と切り替えコストを先に測ってから採用する。
✍️ 編集後記 3 社の対応を並べると、エージェント時代のインフラ設計は、作れるものは安く大量に作り、合意が必要なものは 1 か所に絞るという方針にまとまる。キャッシュ、使い捨てのブランチ、changeset は増やしてかまわないが、ref と本番スキーマは 1 つに保つ。自社のパイプラインで最初に詰まるのは、たいてい後者の「1 つしかないもの」を取り合う箇所だ。
