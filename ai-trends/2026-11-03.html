今号のテーマ AGENT-COST-CONTROL

エージェントのコスト管理は「月末の請求書」から「実行単位の計量と停止」へ — 誰の・どのセッションかで計る、止めずに一時停止する、高い経路は設定で閉じる

10月29日、Anthropic は Usage and Cost Analytics API をベータで公開した。コストをモデルやワークスペースだけでなく、リクエストの背後にいるユーザー・サービスアカウント（actor）、さらに Managed Agents の agent_id や session_id で集計できる。チャットの頃は「API キーごとの月額」を見ていれば足りた。しかしエージェントは 1 回の依頼で数十回モデルを呼び、サブエージェントやサンドボックスの計算資源も消費する。請求書を待ってから原因を探すのでは遅い。同じ時期、OpenAI はプロジェクトごとに使えるサービスティアを制限できるようにし、ホスト型サンドボックスの課金を「アクティブなターンの間だけ」に改めた。GitHub は Copilot を AI クレジットの従量課金に移し、予算を超えたメンバーが増額を申請して承認を待つ流れを GA にした。各社のコスト管理は「計る単位」「止め方」「入口の絞り方」の三層に分かれて設計され始めている。

TL;DR — 3 行で
  • Anthropic の新しい分析 API は、コストを actor（ユーザー / サービスアカウント / キー）や Managed Agents のセッション単位で引ける。ただしデータの反映は通常 4 時間以内で、リアルタイムの制御には使えない
  • リアルタイムの制御は実行単位の上限が担う。Managed Agents のセッション予算は上限に達するとセッションを失敗にせず一時停止し、上限を上げれば中断したターンから再開する。GitHub も予算超過のメンバーに増額申請させる「止めて承認を待つ」流れを採った
  • OpenAI はプロジェクトが使えるサービスティアを組織側で制限できるようにした。金額の上限ではなく、単価の高い処理経路をそもそも使わせない設定で、コスト管理の入口になる
📐 パターン 1: 計る単位は「API キー」から「誰の・どのセッションか」へ

Anthropic の Usage and Cost Analytics API には /v1/organizations/analytics/usage（トークン数・リクエスト数）と /v1/organizations/analytics/cost（USD）の 2 つのエンドポイントがある。group_by[] には最大 5 つのディメンションを指定でき、model・workspace・api_key_id・service_tier に加えて actor を選べる。actor はリクエストの帰属先で、ユーザー、サービスアカウント、AWS / Google Cloud の連携 ID、どれにも当たらなければキーそのものになる。Claude Code がサインイン時に発行するキーの利用は、キーではなくそのメンバーに帰属する。Managed Agents については agent_id・environment_id・deployment_id・session_id が並び、コスト種別（cost_type）にはトークンのほか web_search、code_execution、session_usage が分かれて出る。

キー単位の集計で困るのは、エージェントが共有キーや CI 用のキーで動くからだ。誰の依頼で、どのエージェントの、どの実行がコストを生んだのかが、キーの粒度では消えてしまう。GitHub も同じ問題に「人」の単位で対処している。コストセンターに 1 つのユーザー単位予算を設定すると、メンバーの増減に予算が自動で追従する。ただし、計量の精度と即時性は両立していない。Anthropic の新 API はデータの反映が通常 4 時間以内（最大 24 時間）で、旧 API の「通常 5 分以内」より遅い。月末から約 7 日間は値が改訂され得るとも明記している。細かく計る層は事後の配賦と分析に向けた設計で、実行中に止める用途は別の層に任されている。

Anthropic（Usage and Cost Analytics API、ベータ）
コストを actor・API キー・モデル・サービスティアに加え、Managed Agents の agent / session 単位で集計できる
api_key_ids[] フィルタは「そのキーで認証した全リクエスト」、actor_ids[] は「キー自身に帰属するリクエストだけ」と、キーと帰属先を別の問いとして扱う。データ反映は通常 4 時間以内で、旧 Usage and Cost API は legacy 扱いになった
📄 一次ソース
GitHub Copilot（コストセンターのユーザー単位予算）
個人の予算 → コストセンターのユーザー単位予算 → 全体の既定予算の順で、より具体的な予算を優先して適用する
例として、プラットフォームエンジニアリングのコストセンターは 1 人 $250、それ以外は既定の $40 という設定を挙げる。含まれる利用枠の消費も数えるので、従量課金が始まる前に特定のユーザーを止められる。6月30日時点では REST API からのみ作成できる
📄 一次ソース
示唆: エージェントを社内に配るなら、共有キーを使い回す前に「コストを誰に帰属させるか」を決める。人に紐づくキーかサービスアカウントで認証させ、セッション ID をログに残しておけば、後から配賦できる。ただし、集計 API の遅延を前提にした分析基盤で実行中の暴走は止められないので、停止の仕組みは別に用意する。
📐 パターン 2: 上限に達したら「失敗」ではなく「一時停止して承認を待つ」

Managed Agents のセッション予算は、作成時に budget={"type": "limit", "max_list_cost": {...}} を付けると、そのセッションのモデルトークン費用を公開リスト価格で積算する。サブエージェントのスレッドも含む。上限に達するとターンは stop_reason.type: budget_reached で終わるが、これは失敗ではない。セッションは idle のまま残り、ファイル・ツールの状態・会話はそのまま保持される。sessions.update で上限を上げると running に戻り、追加のメッセージなしで中断したターンから再開する。ストリームを見ていないフリート向けには session.budget_reached の webhook が 1 回飛ぶ。上限の判定はモデルリクエストの合間に行うため、境界をまたいだリクエストは最後まで走る。ドキュメントの例では、$0.10 の上限が $0.12 で止まっている。

「止めるが捨てない」設計に揃ってきた理由ははっきりしている。エージェントの実行は長く、途中で打ち切ると、それまでに使った費用が丸ごと無駄になる。上限は「ここで人間が判断する」チェックポイントとして使うほうが合理的だ。GitHub の予算増額リクエストも同じ形をとる。AI クレジットを使い切ったメンバーは、クレジットを消費する機能だけが止まり、その場で増額を申請できる。組織オーナーや請求管理者が金額を決めて承認すると、すぐに利用が戻る。どちらも金額の上限を「拒否」ではなく「承認フローへの分岐点」として扱っている。なお、Anthropic のセッション予算は「組織・ワークスペース・1 日分のトラフィックではなく、1 回の実行を区切るもの」と明記されていて、既存の組織単位の上限と組み合わせて使う前提になっている。

Claude Managed Agents（セッション予算）
セッション単位の上限に達すると budget_reached で一時停止し、上限を引き上げれば中断したターンから再開する
予算はセッション作成時にしか付けられず、一度外すと付け直せない。また、公開リスト価格のないモデルを含むと model_not_budgetable で作成に失敗する。割引を無視してリスト価格で数えるので、実際の請求額以下で必ず止まる
📄 一次ソース
GitHub Copilot（予算増額リクエスト、GA）
予算を使い切ったメンバーがその場で増額を申請し、予算の所有者（組織 / Enterprise）側で金額を決めて承認する
申請は予算を支払うアカウントの設定画面に届き、「Approve and increase」で予算が引き上げられて即座に利用が戻る。Copilot Business / Enterprise の従量課金が対象で、managed users の Enterprise は対象外
📄 一次ソース
示唆: 長時間走るエージェントに上限を付けるなら、上限到達を「エラーで終了」にせず「状態を保ったまま一時停止」にできるかを確認する。上限は 1 リクエスト分はみ出す前提で少し低めに置き、到達時の通知先（webhook や承認者）を先に決めておく。
📐 パターン 3: 高い経路は金額ではなく設定で閉じる

OpenAI は 10月21日、プラットフォーム設定でプロジェクトごとに使えるサービスティアを選べるようにし、組織設定から全プロジェクトのティアを制限できるようにした。トークン間の生成時間を縮める Ultrafast のような上位ティアを、許可したプロジェクトだけが使える。許可されていないティアを要求すると、遅い応答に落ちるのではなくエラーになる。同じ月の 10月9日には、ホスト型サンドボックスの計算資源の課金を「アクティブなターンの間だけ」に改め、ターン間のアイドル時間は請求しなくなった。事前ウォームアップのドキュメントでは、セッションに接続する前のコンテナ利用は無料で、接続後に通常のコンテナ料金がかかると説明している。

この層は、金額の上限とは別の問題を解いている。エージェントのコストは「何回呼んだか」だけでなく「どの経路で呼んだか」で桁が変わる。上位の処理ティア、長期キャッシュの書き込み、常時起動のサンドボックスなどだ。金額の上限は使った後に効くが、経路の制限は使う前に効く。OpenAI がティア制御を「支出の上限」ではなく「使ってよい処理経路の許可リスト」として出したのはそのためで、組織が既定値を決め、プロジェクトは許された範囲で選ぶ構造になっている。サンドボックスの課金をアクティブなターンに限ったのも、課金の単位をエージェントの実行単位に合わせる変更と読める（これは筆者の解釈）。

OpenAI API（サービスティア制御・サンドボックス課金）
組織とプロジェクトの設定で使えるサービスティアを制限し、ホスト型サンドボックスはアクティブなターンの間だけ課金する
10月21日のティア制御は、許可外のティアを要求するとエラーを返す（エラーガイドに誘導される）。10月9日にはサンドボックスの事前ウォームアップと、ターン間アイドル時間の非課金化が同時に入った
📄 一次ソース
示唆: 予算の上限を決める前に、プロダクトで使ってよいモデル・処理ティア・ホスト型ツールを組織の既定値として絞る。上位ティアはそれが必要なプロジェクトだけに許可すれば、金額アラートが鳴る前に単価の跳ね上がりを防げる。
✍️ 編集後記 エージェントのコストは、トークン単価の問題から「どこで判断を挟むか」の設計問題に変わりつつある。計る層は遅くても細かく、止める層は粗くても即時に、入口の層は使う前に効かせる。三つを一つの仕組みで済ませようとせず、遅延と粒度の違う層を重ねるのが、今回の各社の発表から見える共通の答えだ。
🔗 今号の動向ピックアップ
OpenAI、事前ウォームアップしたサンドボックスの仕様を公開接続前のサンドボックスは 5 分で失効し、接続前の利用は無料。共有環境は最初の接続から 20 分のアイドル寿命を持ち、最大 128 セッションが同じ環境を共有できる。課金がセッションへの接続とアクティブなターンに結び付いている点が、本号の「実行単位で計る」流れと重なる。
Claude、管理者向けの支出可視化と上限アラートを拡充（7月2日）組織の上限の 75% と 90% で管理者に、個人の上限の 75% と 95% でユーザーに通知し、ユーザーはその場で増額を申請できる。チャット・Cowork・Claude Code の既定モデルも管理者が決められる。本号のセッション予算や分析 API より上の、組織・グループ単位の層にあたる。
GitHub Copilot、AI クレジットの従量課金に移行プレミアムリクエストの回数制をやめ、各プランに月次の AI クレジットを含めて、超過分を追加購入する形にした。コード補完と Next Edit suggestions はクレジットを消費しない。本号で扱ったユーザー単位予算と増額申請は、この従量課金を前提にした制御層だ。
