エージェントの長期記憶は「要約」をやめた — 編集可能なファイル、共有された手順、非破壊のグラフへ

個人アシスタントの記憶は「会話の要約」ではなく「編集可能な事実の集合」に置き換わりつつある。2026年8月、AnthropicはClaudeの記憶を会話終了後の要約ではなく、対話中にトピックごとのファイルへ書き込む方式に切り替えた。同年9月にはCursorが、プロジェクト単位でエージェント群が学んだ手順を共有ファイルに蓄積する仕組みを公開した。個人の事実、プロジェクトの手順、監査可能な事実の履歴——記憶の対象が違えば選ぶべき構造も違う。今号はその使い分けを、具体的な実装から追う。

TL;DR — 3 行で
  • Claudeは会話終了後の要約をやめ、対話中にトピック単位のファイルへ直接書き込み、ユーザーが個別に編集できる方式に切り替えた。
  • Cursor Projectsは「個人の事実」ではなく「学んだ手順」を記憶の対象にし、コーディネーターとサブエージェント群がクラウド上の共有ファイルに蓄積し続ける。
  • Zepのようなフレームワーク層は「いつ真だったか」を保持する時間軸付きグラフを採用し、フラットな要約では扱えない監査要件に応える。
📐 パターン 1: 個人アシスタントの記憶は「要約」から「編集可能な事実」へ

2026年8月、Anthropicは Claude の記憶方式を変更した。それまで主流だった「会話終了後にモデルが全体を要約し、その要約を次回の context に差し込む」方式をやめ、対話中にトピックごとのファイルへ直接書き込むようにした。ユーザーは Memory 設定で Topics 一覧からファイルを個別に読み書き・削除でき、会社名の誤りのような事実を1ファイル訂正するだけで、以降の全会話に反映される。

この設計転換の背景には、要約ベースの記憶が抱えていた「訂正が効かない」問題がある。要約は生成のたびに作り直されるため、ユーザーが一度間違いを指摘しても次の要約で再び同じ誤りが復元されかねない。Letta が Sleep-Time Compute で採った解法は少し異なり、応答を返す主エージェントとは別に、アイドル時間帯だけ動く「Sleep-Time エージェント」が非同期に memory block を書き換える。目的は同じく編集の質を上げることだが、対話を止めずに記憶の整理コストを裏側に逃がす点に重心がある。

Claude（Anthropic）
対話中にトピック単位のファイルへ直接書き込み、ユーザーが個別に編集・削除できる
会話終了後の要約生成をやめたことで、一度の訂正が以降の全会話に反映されるようになった。同時期にClaude ChatとCoworkの記憶も統合された。

📐 パターン 2: プロジェクト単位のエージェントは「学んだ手順」を共有ファイルに貯める

Cursor が2026年9月10日に公開した Projects は、記憶の対象を「個人の事実」から「プロジェクトの手順」に移した。コード自体は書かないコーディネーターエージェントが配下のサブエージェント群にタスクを振り、各エージェントが調べたコードベースの構造やテスト手順、作業の進め方の好みを共有ファイル群に書き足していく。あるエージェントがサービスのテスト方法を突き止めれば、以降に立ち上がる別のエージェントは同じ調査をやり直さずに済む。

この共有ファイルはクラウド上のマシンで永続し、ローカルの端末を閉じても止まらない。Slack やPRの監視、スケジュール実行のように、ユーザーが毎回プロンプトを打たなくても再開できる運用を前提にしているためで、Cursor は Projects を主に使うユーザーはマージするPR数が6倍になったと報告している。個人向け記憶が「誰か一人のための事実」を保持するのに対し、こちらは複数のエージェントインスタンスが横断で参照する共有ストックである点が構造的に異なる。

Cursor Projects
コーディネーター配下のサブエージェント群が学んだコードベース知識・テスト手順・作業の好みを、クラウド上で永続する共有ファイルに蓄積する
個人の事実ではなくプロジェクトの運用知識を記憶の対象にしている点が個人アシスタント型の記憶と異なる。Projects利用者はPRのマージ数が6倍という数字も公表されている。

📐 パターン 3: 「いつ真だったか」を残す必要があるなら、要約ではなくグラフを選ぶ

Zepの Graphiti エンジンは、会話ログと構造化されたビジネスデータの両方を、時間軸を持つ知識グラフとして統合する。ノードとエッジで事実を表現し、event time（その事実がいつ現実に起きたか）と ingestion time（システムがいつそれを取り込んだか）を別々に持たせることで、過去のある時点で何が正しいとされていたかまで遡って再現できる。事実は上書きされるのではなく、有効期間が終わった時点で invalid と記録されるだけで、履歴自体は消えない。

フラットな要約やトピックファイルは「今何が正しいか」には強いが、「いつからいつまで正しかったか」は原理的に表現しづらい——要約し直すたびに古い版は失われるためだ。監査や契約変更の追跡のように、過去の状態そのものが問い合わせの対象になる業務データを扱うエージェントでは、この非破壊性が要件になる。Zepはこの設計でDeep Memory Retrievalベンチマークにおいて既存手法を上回る結果を報告している。

Zep（Graphiti）
会話データと業務データを時間軸付きの知識グラフに統合し、event time / ingestion timeの二重タイムスタンプで事実の有効期間を管理する
事実を削除・上書きせずinvalid化するだけなので、過去のある時点で何が真だったかを後から再現できる。Deep Memory Retrievalベンチマークで既存手法を上回る結果を報告。

示唆: 「今の状態」だけでよいなら要約やトピックファイルで十分だが、監査・コンプライアンスのように過去の状態そのものが問われる用途では、非破壊で時間を刻めるグラフ構造を最初から選んでおく方が後から作り直すより安い。
✍️ 編集後記 2026年の記憶実装が割れているのは「ベクトルDBを使うかどうか」ではなく、「いつ記憶を書き換えるか」と「壊れた記憶をどう訂正するか」だ。ライブ書き込み、非同期のバックグラウンド処理、非破壊のグラフ——どれも生の会話ログをそのまま貯めない点では一致している。次に来る論点は、この3層をまたいで記憶を移し替えるコスト——たとえば個人の記憶をプロジェクトの記憶に昇格させる境界線——になるはずだ。
