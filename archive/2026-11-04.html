DEEP DIVE: Postman デスクトップが AI エージェント用プラグインを無断で自動導入

GitHub Issue #14370 で、Postman 12.33.4（macOS）を起動しただけで、Codex プラグイン 1.1.0、Claude Code プラグイン 2.0.1、Postman CLI が利用者の同意なしに入ったと報告された（10 月 25 日付）。ログの導入元は「auto-existing-upgrade」で、既存ユーザーを対象にした自動アップグレード経路だ。Codex の設定には Postman のマーケットプレイスが追加されてプラグインが有効化され、SessionStart フックが「API エンジニアリングに関わる作業では postman:api-engineer スキルを読み込め」という指示をエージェントに注入する。対象は Postman を明示的に頼んだ場面にとどまらず、API が絡む作業全般に広がる。さらに導入処理は、自社フックの trusted_hash を自分で書き込んで承認済みにしており、利用者の判断を経ずにフックが信頼される。11 月 3 日には 12.35.1 でも同じ挙動が再現され、Cursor 向けプラグインの導入も確認された。データの送信は確認されていない。別の利用者の検証では、フックの信頼記録はローカルのプロセスから書き換えられ、Claude Code のプロジェクトフックは非対話実行でも発火した。Postman 側はセットアップ簡略化のための同梱と説明し、既存ユーザー向けのオプトインを明確にすると回答したが、全員オプトインを求める声が多く、Bruno や Insomnia への乗り換えを挙げる人も出た。
🧠 今回の核心は導入そのものより、フックを自己承認する設計にある。エージェントの信頼モデルは「利用者が承認したフックだけが動く」に依存しており、その前提を導入側が迂回できてしまう。データ送信の証拠は出ておらず、実害は未確認だ。ただし Postman の回答は説明にとどまり、承認処理の修正時期は示されていない。修正が出るまでは、同種のデスクトップアプリ全般を疑う根拠になる。
  • Postman 12.33.4 / 12.35.1 で再現。Codex 1.1.0・Claude Code 2.0.1 プラグインと CLI が起動だけで導入される
  • 導入処理が trusted_hash を自前で書いてフックを承認済みにするため、フックの信頼確認ダイアログを通らない
  • SessionStart フックが API 関連の作業全般でスキルの読み込みを指示する。リモート MCP（mcp.postman.com）は認証エラーで失敗
💡 Postman を入れている開発機では、~/.codex の設定と Claude Code のプラグイン一覧を確認し、意図しない項目を外すこと。社内の標準ツールが他ツールの設定を書き換えていないかの棚卸しにもなる。

GitHub、従来比 180 倍のスループットを来年初頭に提供へ（GitHub Universe 2026）

GitHub は、AI エージェントの増加で書き込み負荷が急増していることを受け、Git の基盤を再設計した。計算とストレージを分離し、コードは Azure Blob Storage に置き、Git サーバーは一時キャッシュだけを持つ。書き込みロックをリポジトリ単位からブランチ単位に変えたことで、別ブランチで動くエージェントが並列に作業できる。5,000 体のエージェントが 1 つのリポジトリに毎秒 7,200 件書き込む試験を処理した。
  • 従来は 1 リポジトリへの push が毎秒数十件までだったが、新設計は毎秒数千件を目標にする
  • ブランチ単位ロックだけで 3〜4 倍。残るボトルネックは参照トランザクションで、専用ログサービスが処理する
  • 今年だけで CPU コア 400 万、ストレージ 160PB、帯域 50Tb/s を追加。Azure への移行は来年初頭に完了予定
💡 エージェントで 1 リポジトリに大量 push する運用は、来年初頭まではレート制限に当たりやすい前提で設計し、ブランチを分けて並列化しておくと新方式の恩恵を受けやすい。
