DEEP DIVE: Java4Shell（CVE-2026-114938）: OpenJDK の Base64 デコーダに認証不要の RCE

OpenJDK の x86-64 向け Base64 intrinsic に、ヒープ領域外書き込みの脆弱性が見つかった。calif.io が公開し、Oracle が 11/17 にパッチを出している。HotSpot は AVX-512 VBMI 命令で Base64 を一括デコードするが、入力末尾にパディング（=）が付くと、出力長が 0 のときでも output_len を減算してしまい、-1 または -2 にアンダーフローする。bzhiq(-1, output_len) は output_len が 64 以上だと全ビットが立ったままになるため、ストア用マスクが 0xFFFFFFFFFFFFFFFF となり、確保された出力配列を超えて 64 バイトがそのまま書き込まれる。再現例では 65 バイトの入力に対し出力配列は 50 バイトで、オフセット 48 から 64 バイトを書くため配列末尾を 62 バイト越える。先頭 1 バイトは攻撃者が完全に制御でき、2 バイト目は 4 ビットだけ制御できる。著者らは、配列長を書き換えて任意範囲を読み書きする「writer / reader」手法を示し、デフォルト設定の Keycloak・Jira・Confluence・Artifactory・Jenkins・PingFederate で認証前 RCE が成立すると報告している。JIT コンパイル後の経路でだけ発動するため、PoC はデコードを 20 万回ウォームアップしてから攻撃入力を渡す。
🧠 Heartbleed 型の情報漏えいと RCE を 1 つのバグで両方出せる点は、Java 製の認証基盤が多い現場には重い。実測で示されているのは主要 OSS/製品の既定構成での成立までで、製品別の攻撃チェーンは後日公開と予告されており、悪用が広がる速度は未知数だ。一方、条件が AVX-512 VBMI 搭載 CPU に限られるため、クラウドのインスタンスタイプ次第で影響範囲は大きく変わる。まず自社の JVM が動くホストの CPU 世代を棚卸しすべきだろう。
  • CVSS 4.0 で 9.2（Critical）。OpenJDK 17.0.6 以降と Corretto・Temurin・Zulu など主要ディストリビューション、Oracle Java SE が対象
  • 条件は AVX-512 VBMI を持つ x86-64 CPU（Ice Lake 以降の Xeon、Zen 4 以降の EPYC/Ryzen）。ARM64 は影響を受けない
  • 暫定回避は -XX:-UseBASE64Intrinsics または -XX:UseAVX=2（後者は x86-64 ホスト専用で、ARM の JVM は起動に失敗する）
💡 Java を x86-64 の最近のサーバで動かしているなら、ベンダー提供の修正ビルドへ更新するのが先決で、更新できない間は intrinsic の無効化で当面の被害面を塞げる。
